## 1. 项目概述

### 1.1 一句话定义

一个 Flutter 桌面应用，同时保持与多台网络设备的长连接会话，让运维人员在同一个窗口里编辑命令、按行或按选区下发，并实时查看回显。

### 1.2 背景

网络运维的日常是在十几台到几十台设备之间反复切换、敲命令、看回显。常见的做法是开一堆 SecureCRT / PuTTY 窗口，问题在于：

- 窗口数量随设备数量线性增长，切错窗口是常事
- 同一条配置要在多台设备上重复敲，或者依赖自研脚本
- 命令是从文档、邮件、工单里复制来的，粘贴到终端里容易漏行、错行
- 事后想查"我到底敲了什么、设备回了什么"，终端的历史缓冲靠不住

本工具要解决的是前三点中的**编辑与下发**环节：把"要发哪些命令"变成一件可编辑、可选择、可视化的事，再交给程序按正确的节奏逐条下发。

### 1.3 设计目标

1. **多设备并驻**：多台设备的长连接同时保持，切换设备零等待
2. **下发可控**：命令以文本行的形式先落在编辑区，用户明确指定发送范围后才下发
3. **节奏正确**：网络设备 CLI 必须逐条下发、等回显完成再发下一条，否则命令会串行错乱
4. **输出可信**：输出是该设备会话的完整流，含设备回显，且默认落盘可追溯

### 1.4 非目标

本工具**不是**终端模拟器。它不做全屏 TUI 程序（如 `top`、`vi`）的交互渲染，不追求像素级还原设备终端画面。它的定位是「面向网络设备 CLI 的命令批量下发与回显查看工具」。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| **设备（Device）** | 一台被管理的远端设备，含连接参数与显示名称 |
| **会话（Session）** | 与某台设备建立的一条长连接。一台设备同时最多一条会话 |
| **设备列表** | 左侧面板中按钮形式的设备集合 |
| **当前设备** | 用户选中、编辑区与输出区正在跟随之的设备 |
| **编辑区** | 命令编辑窗口的文本区域 |
| **输出区** | 命令执行输出窗口的文本区域 |
| **命令队列** | 待下发的命令序列，按设备隔离，串行执行 |
| **提示符（Prompt）** | 设备 CLI 等待输入时显示在行尾的标记，如 `[CoreSW]`、`Router#`、`<Huawei>` |
| **静默去抖** | 命中提示符后额外等待一段无新数据的时间，用以排除误判 |
| **翻页提示** | 设备分页输出时的 `--More--` 类标记 |
| **命令库** | 用户维护的可复用命令片段集合，每台设备独立一份 |

## 3. 用户与典型场景

### 3.1 目标用户

负责网络设备日常运维与配置的网络工程师。熟悉设备 CLI，习惯逐条敲命令并观察回显，关心"命令有没有真的生效"。

### 3.2 典型场景

**场景 A：单设备配置下发**
运维人员接到工单，需要在核心交换机上给 8 个接口加描述。他把命令从工单里粘贴进编辑区，检查一遍，拖选这 8 行，点发送，然后盯着输出区逐条确认。中途发现第 5 条写错了，点"停止"，改掉再重发剩下的。

**场景 B：多设备巡检**
运维人员同时连着 6 台设备，逐个点设备按钮切换，在各自编辑区里保留着不同的巡检命令（切回来还在），挨个发送并查看结果。

**场景 C：事后追溯**
三天前某台设备上做过一次配置变更，需要确认当时执行了什么、设备回了什么。从日志目录里直接翻出那天那台设备的记录。

**场景 D：经堡垒机接入**
生产设备在隔离网段，只能经堡垒机跳转。运维人员在工具里配好一次堡垒机，之后新增设备时只需勾选它，不必每台设备重复填一遍堡垒机口令。20 台设备同时在线时，工具对堡垒机只维持一条 SSH 连接、按需开转发通道，不会撞上堡垒机的并发会话限制。

## 4. 功能需求

### 4.1 设备管理（FR-D）

| 编号 | 需求 |
|---|---|
| FR-D-01 | 用户可以添加设备。添加时需填写：**显示名称**（用户指定）、协议（SSH / Telnet）、主机地址、端口、用户名、密码 |
| FR-D-02 | 协议为 SSH 时，可选使用私钥文件认证替代密码认证 |
| FR-D-03 | 端口默认值：SSH 为 22，Telnet 为 23；用户可覆盖 |
| FR-D-04 | **显示名称在设备列表内必须唯一**。添加或编辑时若重名，给出明确提示并拒绝保存 |
| FR-D-05 | 用户可以编辑已有设备的任意字段 |
| FR-D-06 | 用户可以删除设备。删除前二次确认。删除时断开其连接，并一并删除其草稿与命令库；**日志文件保留** |
| FR-D-07 | 用户可以调整设备在列表中的顺序（拖拽排序） |
| FR-D-08 | 设备列表**用按钮形式**呈现，每个按钮显示设备名称与其连接状态 |
| FR-D-09 | 设备按钮上的状态指示：灰=未连接，黄=连接中或重连中，绿=已连接，红=连接失败或已断开 |
| FR-D-10 | 设备列表在应用重启后完整恢复 |
| FR-D-11 | 每台设备可配置「登录后执行」命令列表（多行文本），见 FR-C-08 |
| FR-D-12 | 每台设备可标记「启动时自动连接」，见 FR-C-14 |
| ~~FR-D-13~~ | **已作废（2026-09-25）**：跳板机支持整体放弃，V1 不实现。原要求：每台设备可指定**一台**跳板机（0 个表示直连）。见 §4.2.1 与 §10.2 |

### 4.2 连接管理（FR-C）

| 编号 | 需求 |
|---|---|
| FR-C-01 | 应用**同时保持多台设备**的连接，互不干扰 |
| FR-C-02 | 采用**长连接常驻**模型：设备连接建立后持续保持，不因命令执行完毕而断开 |
| FR-C-03 | 点击设备按钮 = 将其设为当前设备。若该设备尚未连接，**同时发起连接** |
| FR-C-04 | 点击已连接的设备按钮仅做切换，不断开连接 |
| FR-C-05 | 用户可以在设备编辑对话框中主动断开某台设备的连接 |
| FR-C-06 | 连接失败时，设备按钮变红，并在输出区给出可读的失败原因（连接超时 / 认证失败 / 主机不可达 / 协议错误 / 主机密钥校验未通过，见 §13.15） |
| FR-C-07 | **断线自动重连**：检测到会话意外断开后，按指数退避自动重连：1s → 2s → 4s → 8s → 16s → 30s 封顶，此后维持 30s 间隔持续重试 |
| FR-C-08 | 连接成功后，自动依次下发该设备的「登录后执行」命令（如 Cisco 的 `enable`）。**每次重连成功都要重新执行** |
| FR-C-09 | 重连成功时，在输出区插入一条醒目的分隔标记，标明断线时段与重连时刻 |
| FR-C-10 | 断线时，**命令队列中尚未发出的命令一律丢弃，不自动重放**。输出区给出告警 |
| FR-C-11 | SSH 首次连接某主机时，弹出主机密钥指纹供用户确认，确认后保存。设置中可全局关闭该校验 |
| FR-C-12 | 关闭应用时，直接关闭所有会话，**不向设备发送任何命令**（避免意外改变设备状态） |
| FR-C-13 | 连接超时默认 15 秒，可在设置中调整 |
| FR-C-14 | 被标记为「启动时自动连接」的设备，在应用启动后自动发起连接 |

**FR-C-10 的理由**：网络设备上的命令多为配置下发。断线重连后自动重放队列，可能导致同一条配置被下发两次（例如 `interface X` / `shutdown` 这类命令重复执行后果不可逆）。宁可让用户重新确认。

### 4.2.1 跳板机（FR-J）—— **V1 已整体作废（2026-09-25）**

> **本节全部需求 FR-J-01 ~ FR-J-07 在 V1 中不实现。** 2026-09-24 曾把范围收缩为
> 「只做单跳」（推迟 N 跳链与连接复用）；**2026-09-25 用户进一步决定放弃支持跳板机**，
> 于是单跳那一半也不再做 —— `SshTunnelConnector` 不建，设备编辑对话框不提供跳板机选择，
> 设置里不提供跳板机标签页。理由与取舍见 §10.2。
>
> **本节文字全部保留，作为 V1.1 的设计输入**，不是待办。下面表格里所有
> 「V1：…」的表述一律读作「**V1 不做这件事**；这是 V1.1 恢复跳板机时的目标形状」，
> 「已推迟到 V1.1」也一律读作「V1 不做」。以本行为准，不再逐行改写。

设备位于隔离网段、必须经堡垒机才能访问时，使用 SSH 跳板机（等价于 OpenSSH 的 `ProxyJump`）。

| 编号 | 需求 |
|---|---|
| FR-J-01 | 用户可以添加、编辑、删除跳板机。字段：名称、主机地址、端口、用户名、密码或私钥文件 |
| FR-J-02 | 跳板机列表**全局共享**，不随设备重复定义。这样堡垒机口令变更时只需改一处 |
| FR-J-03 | V1：每台设备可指定 **0 或 1 台**跳板机（0 = 直连，1 = 单跳）。**多跳链（N 个）已推迟到 V1.1**（2026-09-24 决定，理由见 §10.2） |
| FR-J-04 | V1：连接时先建立到该跳板机的 SSH 连接并完成认证，再在其上开转发通道连到设备 |
| FR-J-05 | 跳板机这一跳失败时，错误信息必须**指明是哪一跳失败**（如「第 1 跳 堡垒机-A 认证失败」），便于定位。V1 只有一跳，但**文案与分类接口按多跳设计**（`JumpHop`/`hop:` 参数保留），恢复到多跳时不必改接口 |
| FR-J-06 | 跳板机这一跳同样需遵守 FR-C-11 的主机密钥校验规则 |
| FR-J-07 | **已推迟到 V1.1**（2026-09-24 决定）。原要求：同一跳板机链的**前缀连接在多个设备间复用** —— N 台设备共用同一台跳板机时只建立 1 条 SSH 连接，为每台设备各开一条转发通道，按引用计数释放。V1 为**每台设备各建一条**到跳板机的连接 |

**FR-J-07 的理由（保留，供 V1.1 使用）**：堡垒机普遍限制单用户的并发会话数（常见 5～10）。若每台设备各建一条到堡垒机的连接，接 20 台设备会直接撞上限制，且失败原因难以诊断。dartssh2 的转发通道天然支持一条 SSH 连接上开多个 `direct-tcpip` 通道，因此复用的边际成本很低。**V1 接受这个限制**：并发设备数受堡垒机上限约束，且撞上限制时会以可读的连接失败呈现（FR-C-06），不是静默出错。

**FR-J-01/FR-J-02 的理由**：堡垒机是共享基础设施，若把凭据内联进每台设备，改一次堡垒机口令要编辑全部设备。

### 4.3 命令编辑与下发（FR-E）

| 编号 | 需求 |
|---|---|
| FR-E-01 | 编辑区支持输入任意行命令，支持多行文本 |
| FR-E-02 | 编辑区左侧显示行号 |
| FR-E-03 | 编辑区内容**按设备独立保存**。切换设备时编辑区整体切换；切回时内容仍在 |
| FR-E-04 | 编辑区草稿在应用退出时落盘，重启后恢复 |
| FR-E-05 | 用户可以用鼠标点击定位光标到任意行 |
| FR-E-06 | 点击「发送」按钮时的发送范围：**有选中文本时发送选中的所有行；无选中时发送光标所在的那一行** |
| FR-E-07 | 发送时按编辑区中自上而下的顺序下发 |
| FR-E-08 | **完全空白的行在发送时被跳过**（不产生空回车污染回显）。确需发送空行时，在行内输入一个空格 |
| FR-E-09 | 每条命令自动补行尾符。默认 `\n`，可按设备切换为 `\r\n` |
| FR-E-10 | 下发采用**串行**方式：发第 N 条 → 等待该条执行完成 → 再发第 N+1 条。同一设备同一时刻只有一条命令在途 |
| FR-E-11 | 「执行完成」的判定见 §5.2 |
| FR-E-12 | 命令执行超时（默认 10s）时，输出区插入醒目告警行，并**强制放行下一条**，避免整个队列卡死 |
| FR-E-13 | 用户可以**中止命令队列**：点击「停止」后，不再发送队列中剩余的命令；已发出的命令不做处理 |
| FR-E-14 | 编辑区中正在发送的行，以及队列进度（如「执行中 3/8」）需要可视化指示 |
| FR-E-15 | 支持从本地文件导入命令到编辑区。导入时询问「替换现有内容」或「追加到末尾」 |
| FR-E-16 | 导入仅支持 UTF-8 编码。遇到非 UTF-8 内容时给出明确提示，而非静默乱码 |
| FR-E-17 | 支持把当前编辑区内容同步给另一台设备：选择目标设备后，指定「覆盖」或「追加」到目标设备的草稿。用于同一条命令需要在多台设备上执行的场景 |

### 4.4 输出显示（FR-O）

| 编号 | 需求 |
|---|---|
| FR-O-01 | 输出区显示当前设备的会话输出流，**包含设备回显**（即能看到"我发了什么"和"设备回了什么"）。其观感接近真实终端 |
| FR-O-02 | 输出区**不做**「命令 → 输出」的分组关联。原因：同一条命令可能被反复执行，把它与某一次输出绑定在语义上不成立 |
| FR-O-03 | 输出内容为**纯文本流**：剥离非 SGR 的 ANSI 控制序列（光标移动、擦除、定位等），保留 SGR 颜色序列并渲染为带颜色的文字 |
| FR-O-04 | 输出自动滚动到底部；用户手动向上滚动时暂停自动滚动，滚回底部后恢复 |
| FR-O-05 | 提供「清屏」按钮：仅清空显示内容，**不影响日志文件** |
| FR-O-06 | 输出区文本可被鼠标选中并复制 |
| FR-O-07 | 输出缓冲区有上限（默认保留最近 5000 行），超出部分丢弃最旧的行。日志文件不受此限制 |
| FR-O-08 | 输出区顶部标题栏显示当前设备名，使"看到的是哪台设备"始终明确 |
| FR-O-09 | 切换设备时，输出区整体切换为该设备的输出流；各设备的输出缓冲各自保留 |

### 4.5 命令库（FR-S）

| 编号 | 需求 |

| FR-S-04 | 命令库可增删改，随设备配置一并持久化 |

|---|---|

| FR-G-03 | 每台设备可覆盖的设置：行尾符、提示符正则 |

## 5. 关键行为规则（详细定义）

本节是实现与验收的直接依据，规则的边界情况必须按此实现。

### 5.1 发送范围判定

```
if (编辑区存在非空选中范围) {
    取出选中范围内覆盖的所有行，按自上而下顺序
} else {
    取出光标所在的那一行（光标视为落在该行内）
}
过滤掉完全空白的行
若结果为空 → 不发送，给出轻提示
```

- 选中范围跨越部分行时，**该行只要被选中范围覆盖到任意一个字符，即整行参与发送**
- 选中范围的行序始终按编辑区自上而下，与用户拖拽方向无关

### 5.2 命令执行完成的判定

一条命令发出后，满足以下**全部**条件才判定其执行完成：

1. **提示符命中**：接收缓冲区中**最后一个非空行**（去掉行尾空白后）匹配提示符正则
2. **静默去抖**：自最后一个字节到达起，连续 **120ms**（可配）没有新数据到达

判定完成后立即释放队列，下发下一条。

**提示符正则默认值**：`[>#\]]\s*$`

覆盖华为 VRP（`<Huawei>` / `[Huawei]` / `[Huawei-GE0/0/1]`）、Cisco IOS（`Router>` / `Router#` / `Router(config)#`）、H3C 等主流形态。

**超时**：命令发出后 **10s**（可配）仍未满足上述条件，则：

- 在输出区插入醒目告警行，注明超时的命令序号与原命令文本
- **强制放行**下一条，队列继续

**为什么需要静默去抖**：设备回显中可能出现以 `>` 或 `]` 结尾的内容行。若只看正则命中最末尾，会在数据仍在流动时误判命令已结束。要求"数据停住 120ms"可以排除绝大多数误判。

### 5.3 翻页处理

- 检测接收缓冲区尾部是否存在翻页提示
- 默认匹配模式：`---- More ----`（华为/H3C）、`--More--`（Cisco）、`<--- More --->`，可在设置中扩充
- 命中后**立即回送一个空格**继续翻页
- 翻页动作**不计入命令队列**，也**不重置**提示符判定的静默计时器所属的命令
- 翻页不被视为"新命令"，因此不产生队列进度变化

### 5.4 断线与重连

| 事件 | 行为 |
|---|---|
| 检测到会话断开 | 设备按钮变黄（重连中）；输出区插入醒目标记；命令队列中未发出的命令全部丢弃并告警；启动指数退避重连 |
| 重连成功 | 设备按钮变绿；输出区插入分隔标记；自动重新执行「登录后执行」命令 |
| 重连失败 | 按退避序列继续重试，按钮维持黄色；连续失败在输出区给出提示，避免刷屏（同一原因只提示一次） |
| 用户主动断开 | 停止重连，按钮变灰 |

### 5.5 设备切换

切换设备时，以下内容**整体**随之切换：

- 编辑区内容（含光标位置与滚动位置）
- 输出区内容（含滚动位置）
- 命令库面板
- 输出区标题栏中的设备名

以下内容**不**随切换变化：

- 各设备的连接状态（后台保持）
- 各设备的命令队列（在后台继续执行，输出写入各自缓冲区）
- 日志写入（持续进行）

**注意**：在设备 A 的队列执行期间切到设备 B，A 的队列**继续执行**，输出写入 A 的缓冲区。切回 A 时能看到完整过程。

### 5.7 跳板机连接 —— **V1 不实现（2026-09-25 决定）**

> 本节描述的是**跳板机实现之后**的行为规则。V1 不建跳板机（§4.2.1、§10.2），
> 因此本节每一条规则在 V1 里都**没有对应的代码路径**：`ConnectorResolver`
> 恒返回 `DirectConnector`，`classifyConnectionFailure` 的 `hop` 形参恒为 null。
> 文字保留，作为 V1.1 的设计输入与恢复时的验收口径。

建立一条经跳板机链 `[A, B]` 到目标设备的连接，实际过程为：

```
连接 A（SSH 直连）
  └─ 在 A 上开 direct-tcpip 通道，目标 = B:22        ← 得到一个双向字节流
       └─ 在该字节流上建立到 B 的 SSH 连接
            └─ 在 B 上开 direct-tcpip 通道，目标 = 设备:22
                 └─ 在该字节流上建立到设备的 SSH 连接（或运行 Telnet 协议）
```

| 规则 | 说明 |
|---|---|
| **逐跳认证** | V1 只有一跳：用该跳板机自己配置的凭据认证。（多跳时每一跳各用自己的凭据 —— 设计不变，只是 V1 链长为 1） |
| **逐跳校验主机密钥** | V1 只有一跳：该跳遵循 FR-C-11，首次连接需确认它的指纹 |
| **通道而非端口** | 使用 `direct-tcpip` 通道，**不在本地绑定任何端口**。因此不会与其他程序争抢端口，也不引入本地监听的安全面 |
| ~~**前缀复用**~~ | **已推迟（FR-J-07）**。原设计：链 `[A]`、`[A, B]`、`[A, C]` 复用同一条到 A 的连接 |
| ~~**引用计数释放**~~ | **已推迟（FR-J-07）**。原设计：每台设备的会话对链上每个前缀各持有一个引用，归零则关闭。**V1 每台设备各建一条到跳板机的连接** |
| **跳板机断线** | 跳板机连接断开会使**所有经由它的设备同时断线**，各自独立进入 FR-C-07 的重连流程。输出区需明确提示这是跳板机导致的批量断线，而非各设备各自故障 |
| **不在设备列表中展示** | 跳板机不作为设备出现，仅在连接链中隐式存在，其状态通过受影响设备的按钮状态间接体现 |

### 8.4 风险与待验证项

**Telnet 层自研的决策依据**：原本的候选 `ctelnet` 0.3.1 有两个问题 —— ① 构造函数只接受 `host`/`port`，内部硬编码 `RawSocket.connect`，**没有 socket 注入点**，因此无法走跳板机（跳板机已于 2026-09-25 整体放弃，但**同一个注入点也是 SOCKS5/HTTP 代理这一 V1.1 候选的前提**，所以这条理由仍然成立）；② 小包，2024 年后未更新。自研约 200 行可同时解决这两点，并去掉一个不受控的依赖。（顺带记录：pub.dev 上另一个主流包 `telnet` 锁定 `sdk: >=2.14.0 <3.0.0`，在本项目的 Dart 3.12 上**根本无法解析依赖**，从一开始就不在候选内。）

| 风险 | 影响 | 应对 |
|---|---|---|
| **自研 Telnet 层的兼容性** | Telnet 选项协商在真实设备上存在差异（回显模式、终端类型、窗口大小），自研实现可能有覆盖不到的组合 | ① 假设备服务器覆盖主流协商组合并做回归；② 协商异常时把完整收发字节记入日志便于定位；③ Telnet 设备多为内网环境，风险可控 |
| ~~**跳板机连接池的生命周期**~~ | **随跳板机整体放弃而消失（2026-09-25）**。原风险：引用计数出错会导致连接泄漏（占满堡垒机会话额度）或提前关闭（在用设备断线）。V1 没有跳板机、也没有池，这个风险不存在；恢复跳板机（无论单跳还是复用）时要重新引入本节措施 |
| **提示符正则的误判** | 设备回显中出现以 `>` / `]` 结尾的内容行会导致误判命令已结束 | 静默去抖（120ms）+ 只看缓冲区最后一个非空行 + 正则可按设备覆盖 |
| **Windows 产物构建** | Linux 开发机无法产出 Windows 桌面包 | 实现阶段落实 Windows 机器或 CI（GitHub Actions `windows-latest`） |
| **非 UTF-8 配置脚本** | 中文环境下存在 GBK 编码的配置文件，导入会乱码 | V1 仅支持 UTF-8 并给出明确提示；GBK 支持列入 V1.1 候选 |
| **明文凭据** | 配置文件泄露即凭据泄露 | 已接受该风险。存储接口独立封装，为后续替换预留（NFR-S-01） |
| **旧设备只提供已被淘汰的 SSH 算法** | `dartssh2` 4.x 已从默认算法集中移除 `ssh-rsa`/SHA-1、`diffie-hellman-group14-sha1`、`aes128-cbc`/`aes256-cbc`、`hmac-md5` 等。只提供这些算法的老设备**直接协商失败**，表现为「连不上」，而本工具的目标设备里这类机器占比不低 | **V1 明确不做兼容开关**（见 §10.1），失败时按 FR-C-06 给出可读原因。缓解：算法集在 `dartssh2` 里是 `SSHAlgorithms` 的一个参数，后续补充为纯增量改动，不需要动 `Connector`/`Session` 抽象 |

### 9.3 端到端测试

在测试中启动一个**假设备服务器**（纯 Dart 实现，提供回显 + 可配置提示符 + 可注入 `--More--` 分页 + 可模拟断线），跑完整链路：

编辑区输入 → 发送 → 队列串行下发 → 提示符判定 → 输出渲染 → 日志落盘

该假服务器同时用于 Telnet 与 SSH 两条链路。**SSH 侧的结论已由调研落实（2026-09-24）**：`dartssh2` **不提供 SSH 服务端**（无 `SSHServer` 之类的 API），因此原定的「用 dartssh2 的服务端能力」不可行。替代方案按可用性分两层：

1. **真 `sshd` 回环集成测试（首选）**：在测试里用 `ssh-keygen` 现生成主机密钥与用户密钥，起一个监听 `127.0.0.1` 高位端口的 `sshd`，跑真实链路。已验证本机具备 `/usr/sbin/sshd` 与 `/usr/bin/ssh-keygen`（OpenSSH 8.0p1），且探测工程 `/tmp/wct-ssh-probe` 中 9/9 用例通过。**该测试必须带同步的可用性跳过守卫**（`sshd` 不存在、端口不可用、Windows 上无 `sshd` 时 `skip:` 而非失败），否则会在 CI 与 Windows 开发机上变成红灯。
2. **纯 Dart 单元测试（打底，始终运行）**：`Connection` ↔ `SSHSocket` 双向适配器、错误分类（FR-C-06 的五种原因）、以及 `SshSession` 的本地私钥加载失败翻译（§13.19-9）都做成不依赖真实 sshd 的纯逻辑测试，用假 `Connection`/假 `SSHSession` 驱动。**连接池的引用计数与前缀复用属 FR-J-07，已推迟，V1 不写这部分测试。**

即：**能用真 sshd 的地方用真 sshd，不能用跳过，但打底的单元测试永远跑。**

## 10. 范围边界

### 10.1 V1 明确不做

| 不做项 | 说明 |
|---|---|
| 多设备群发 | 一次只对当前选中设备下发。设备按钮为单选 |
| 「命令 → 输出」分组关联 | 同一条命令可能重复执行，绑定语义上不成立。输出为统一流 |
| 输出区搜索/过滤 | 输出为统一流，V1 不做检索 |
| 完整终端仿真（xterm） | 见 §8.1 |
| 语法高亮 | V1 不引入 |
| SFTP / 文件传输 | 不在范围内 |
| 凭据加密存储 | 接口预留，实现留待后续（NFR-S-01） |
| 设备分组 / 文件夹 | V1 为平铺列表 |
| macOS 支持 | 不纳入 V1 交付范围 |
| 自动关闭设备分页 | 不做。不主动向设备发送厂商相关的初始化命令，改由用户通过「登录后执行」自行配置 |
| GBK 等非 UTF-8 编码导入 | V1 仅支持 UTF-8 |
| SOCKS5 / HTTP CONNECT 代理 | V1 不做任何代理。`Connector` 抽象层已预留，后续补充实现为纯增量 |
| **跳板机（SSH 跳板机 / 堡垒机，整块）** | **V1 完全不做**（2026-09-25 决定，**取代** 2026-09-24 的「只做单跳」）。`SshTunnelConnector` 不建、跳板机管理界面不建、FR-J-01 ~ FR-J-07 全部不实现。见 §10.2 |
| 跳板机的图形化管理之外的自动化 | 随跳板机整体放弃，V1 无此项 |
| 旧 SSH 算法的兼容开关 | `dartssh2` 4.x 默认算法集不含 `ssh-rsa`/SHA-1、`group14-sha1`、`aes*-cbc`、`hmac-md5`。**V1 不提供开启它们的设置项**：只提供这些算法的设备将协商失败（按 FR-C-06 报可读原因）。理由见 §10.2 |

### 10.2 已明确接受的风险

- V1 凭据以明文存储于 `devices.json`
- Telnet 协议本身明文传输（这是协议固有属性，非本工具的决策）
- **跳板机支持整体放弃**（2026-09-25 决定，**取代** 2026-09-24 的「只做单跳」）

  2026-09-24 曾把 FR-J 收缩为「只做单跳」，推迟 N 跳链（FR-J-03）与连接复用（FR-J-07）。
  2026-09-25 用户进一步决定：**跳板机在 V1 里整体不做**。于是单跳那一半也一并放弃 ——
  `SshTunnelConnector` 不建、设置里不提供跳板机标签页、设备编辑对话框不提供跳板机选择、
  FR-J-01 ~ FR-J-07 全部不实现。

  取舍：需要经堡垒机才能访问的设备在 V1 里**连不上**。这是本决策的主要代价，
  且它**不满足**本文件别处反复使用的「可见且可诊断」这条标准 —— 用户看到的是普通的
  连接超时或主机不可达（FR-C-06 报的是**直连**失败的原因），**看不出"本该走跳板机"**。
  之所以仍然接受：跳板机是**增量拓扑**，不是既有路径的替代；V1 的核心价值
  （多设备长连接 + 命令下发 + 输出回流）在直连场景下完整成立；且这块留到 V1.1
  一次性做对（含复用）比先做一半、回头再改链长更划算。

  两点缓解：① **架构不受影响** —— `Connector` 抽象、`ConnectionSocket` 适配器、
  注入式 `ConnectorResolver` 都在，恢复是纯增量；**分类接口按多跳设计并已保留**
  （`JumpHop`、`ConnectionFailureKind.jumpHostFailed`、`hop:` 形参，以及对应的用例），
  恢复时不必改接口、不必补分类测试；② 已列入 §12 的 V1.1 候选。

  **连带项的定论（原留给计划 4 决定，2026-09-25 定）**：`DeviceProfile.jumpHostIds`
  保留为**列表**类型，`JumpHost` 模型、`jumpHostFailed` / `JumpHop` / `hop:` 形参
  一律原样保留 —— 全部当作**惰性代码**，不改、不删。理由：它们都已评审冻结，
  删改是**净增**工作量；保留则恢复跳板机时零接口改动。代价只有两处，且都已处理：
  ① `devices.json` 里跳板机字段**原样往返但不使用**，非空 `jumpHostIds` 在加载时
  **上报**（见 §8.6），避免"以为走了堡垒机、其实直连"这种看不见的错；
  ② 生产路径上 `hop` 恒为 null，`jumpHostFailed` 这一类**今天不可达** —— 这一点
  必须在计划 5 的颜色/图标口径里说清楚，**别为它设计专属外观**（见 §13.19-5）。

- **V1 只使用 `dartssh2` 的现代算法默认集，不提供旧算法兼容开关**（2026-09-24 决定）

  取舍：加上兼容开关意味着「每台设备多一个安全等级需要用户理解」，且开关一旦存在，用户遇到连接失败的第一反应会是「打开它」，从而在**本可以协商强加密**的设备和链路上也降级到 SHA-1/CBC。反过来，不加开关的代价是部分老设备在 V1 里连不上 —— 这个代价是**可见且可诊断**的（FR-C-06 会报协议错误），而不是静默的安全降级。

  三点缓解：① 该决策**不阻塞**任何架构 —— `SSHAlgorithms` 是 `dartssh2` 连接参数，后续补充只需改 `SshSession` 内部，`Connector`/`Session` 抽象不动；② 失败设备会走 FR-C-06 的可读原因路径，用户能立刻分清「连不上是因为算法」而不是逐个排查网络；③ 已列入 §12 的 V1.1 候选。

## 13. 实现阶段约束（执行期补充）

**13.2 设备顺序是隐式的**

§8.6 的 `devices.json` 没有 order 字段，数组顺序**就是**显示顺序。计划 4 必须保序（读写都不得重排）；计划 5 的拖拽排序（FR-D-07）要靠重写数组实现，**不能靠排序**。

**13.3 损坏的配置文件按条目隔离恢复**

**13.5 SSH 主机密钥指纹需要持久化，但模型里没有对应字段**

FR-C-11 要求首次连接确认后**保存**指纹（原文并列引用的 FR-J-06 是跳板机那一跳的同款要求，随跳板机整体放弃而作废，见 §10.2；FR-C-11 本身不受影响）。计划 2 早于计划 4，因此计划 2 必须接受一个**注入的**指纹存储或回调，而不是自己写文件 —— 否则持久化边界会漏成两处。

**计划 2 冻结的接口形状**（`lib/connection/known_host.dart`）：`find(host, port, keyType)`、`save(KnownHost)`、`remove(host, port, keyType)`，外加 `InMemoryHostKeyStore` 作为内存实现。三条都是必需的，不是"够用就行"：

- **`remove` 不可或缺。** 设备确实更换过主机密钥时，`find` 会一直返回旧指纹，这台设备就被**永久**拒绝连接；而计划 2/3 的错误文案正是让用户"在设置中清除该主机的记录后重连"。接口若只有 `find`/`save`，那句话就是在教用户做一件做不到的事。FR-G-01 里对应的设置项由计划 5 落地。
- **按 `keyType` 分别存储。** 同一主机可同时提供多种算法的主机密钥，每把指纹不同。只按 `host:port` 存一条的话，设备换一种算法协商就会被判成"主机密钥变了" —— 正常的算法协商被报成疑似中间人攻击。用户会因此学会忽略这个警告，而那是最不该被训练成忽略的警告。代价是**算法降级会重新弹一次首次连接确认**（而非报不匹配），这与 OpenSSH 的 `known_hosts` 逐密钥类型存储一致，是有意为之。
- **条目键名 `{host, port, keyType, fingerprint}` 由计划 2 的测试钉死**，计划 4 的持久化必须沿用。钉的是**条目**的键，不含文件外层信封（数组还是映射、`schemaVersion` 等仍由计划 4 按 NFR-R-04 决定）。改名不会报错，只会让已存的文件读不出来 —— 于是每台设备都被当成"首次连接"，**已经变过密钥的主机也会被重新 TOFU 接受**。
- **`keyType` 不得含冒号，构造函数强制。** 记录键是 `'$host:$port:$keyType'` 拼出来的，冒号即分隔符；算法名里再出现冒号，分隔就失去意义 —— 实测 `{host:'h:22', port:1, keyType:'2'}` 与 `{host:'h', port:22, keyType:'1:2'}` 都拼成 `h:22:1:2`，两条记录塌成一条，`find` 返回另一台设备的指纹，又是一次"主机密钥变更"误报。dartssh2 的七个算法名（`SSHHostkeyType`）都不含冒号，所以这只在手改/损坏的文件里触发；而 `fromJson` 正是与空指纹同一条不可信路径，因此和它用同一道守卫。**注意两道守卫都抛 `ArgumentError`** —— 这正是 §13.3 要求计划 4 的逐条目 catch 放宽到"任何构造错误"的原因。

**计划 4/5 的接缝（已知，无需现在决定）：** 接口没有**枚举**方法，`InMemoryHostKeyStore.all` 只服务于测试。FR-G-01 的"已知主机密钥记录的**查看**"因此需要计划 4 的具体 store 自己提供一个列表方法（或给接口补一个 `all`）—— 到那时再定，别让计划 5 的设置界面去 downcast 具体类型。`remove` 已覆盖"逐条清除"那一半。

**已知残留：字符串键在查找路径上仍有歧义（计划 2 刻意不修，计划 4 必须挑一种）**

记录键是 `'$host:$port:$keyType'` 拼出来的。构造函数禁止含冒号的 `keyType`，于是**两条可存储的记录永远不会撞键**（实测：378 组三元组穷举，0 碰撞）—— 记录塌成一条这个危害已经关闭。但 `find`/`remove` 收的是裸 `String`，不做任何校验，所以一个含冒号的 `keyType` 传进去仍会算出别人家的键：

```
find('h', 22, '1:2')   -> 返回 ('h:22', 1, '2') 那条记录
remove('h', 22, '1:2') -> 把那一条删掉
```

**今天不可达**：真实调用方传的 `keyType` 只有两个来源 —— dartssh2 的封闭算法集（七个，全部不含冒号）和本 store 里已存记录（构造函数保证不含冒号）。所以这是一个潜在的 API 不对称，不是现网缺陷。计划 2 不修它，因为修法属于计划 4 的实现选择：

1. 在 `find`/`remove` 里也校验 `keyType`。最省事，但不变式从此依赖三处校验器，而不是让键本身无歧义。
2. **把 map 的键换成元组**（`Map<(String, int, String), KnownHost>`）。碰撞从"被守卫挡住"变成"结构上不可能"，冒号问题连同"构造函数强制、查找路径不强制"这个别扭形状一起消失。**若计划 4 自己实现字符串键的 store，请选这一种**，并且不要把 `KnownHost.identity` 直接当持久化的去重键 —— 它是给人看的/日志用的，不是安全的复合键。

**13.6 列表字段目前是可变的共享引用**

`fromJson` 里 `jumpHostIds` 等用 `.cast<String>()`，返回的是惰性校验视图，且与调用方共享底层 list；`copyWith` 把同一个实例原样传下去。计划 5 的状态层若依赖 `==` 做变更检测会踩到。计划 4/5 视需要收紧为 `List.unmodifiable`。

**13.7 模型没有 `==` / `hashCode`**

目前一律按引用比较，这也是目前往返测试要逐字段写十几行 `expect` 的原因。计划 5 的 Riverpod 状态 diff、列表去重可能会需要值相等；若要补，优先补字段最少、最可能被 keyed 的 `Snippet`。

**13.8 `copyWith` 对「null 是有语义的值」的字段必须用哨兵**

这条约束适用于**任何**后续新增的模型类（计划 2 的 `KnownHost`、计划 4 的草稿模型等），不只是已经改好的那四个字段。

若某个可空字段的 `null` 表示一个**有定义的语义**（而不是「没有这个值」），它的 `copyWith` 参数就**不能**写成 `String? x` + `x ?? this.x` —— 那样「调用方没传」与「调用方显式传 null」不可区分，用户「清空」的操作会被静默变成「保持原值」，且返回一个完全合法的对象、不报任何错。

正确写法是哨兵，给出三种状态（不传→保留、显式 `null`→清空、传值→覆盖）：

```dart
const Object _unset = Object();   // 每个库一份，私有名不会跨库冲突

Foo copyWith({Object? bar = _unset}) => Foo(
      bar: identical(bar, _unset) ? this.bar : bar as String?,
    );
```

已按此改的字段：`DeviceProfile.password` / `.privateKeyPath` / `.promptRegex`、`JumpHost.password` / `.privateKeyPath`、`AppSettings.logDir`。

注意 `Object?` 参数会让**静态类型检查在这几个参数上失效**（传错类型能通过编译，运行时才抛 `TypeError`）—— 这是该惯用法的既定代价，换来的是三态语义正确。代价是「失败得更晚但仍然响亮」，不是「静默失败」。

判据是：**这个字段的 null 有没有语义**。列表字段（`jumpHostIds` 等）不该用哨兵，因为它们的「清空」是 `[]`，是个值不是 null。

**13.9 翻页提示会匹配提示符正则，判定「命令完成」时必须显式排除**

§5.2 的默认提示符正则是 `[>#\]]\s*$`，§5.3 的第三个默认翻页模式 `<--- More --->` **以 `>` 结尾**，因此它同时满足两者：

```
翻页尾巴=true  提示符匹配=true    <--- More --->
翻页尾巴=true  提示符匹配=false   ---- More ----
翻页尾巴=true  提示符匹配=false   --More--
```

后果不是「多翻一页」而是**命令静默丢失**：翻页分支回送空格后，静默去抖到点，`<--- More --->` 被当成提示符，命令被判为完成，下一条命令随即写进一个仍在等待翻页按键的设备 —— 该设备把这些字节当作翻页键吃掉，命令从未执行。用户看到「已发送、已完成」，配置却没生效（典型：`display current-configuration` 之后跟 `save`）。只要设备出下一页的耗时超过去抖阈值（120ms），在负载高或链路慢时就必然触发。

**约束：任何判定「命令结束」的地方，都要先排除翻页尾巴，再看提示符正则。** 这条不只约束计划 1 的 `CommandDispatcher`，也约束计划 2 的 `SshSession`（若它也做提示符判定）与计划 5 中任何重新推导命令状态的显示逻辑。

不要靠**修改翻页模式或提示符正则**来回避 —— 把 `<--- More --->` 改掉会破坏 H3C 设备识别。正确的修法是在「判定完成」这一步做排除。（对应 §8.4 风险表中「提示符误判」一项的具体形态。）

**13.10 未决缺口：翻页状态在超时或批次结束后会丢失**

承接 13.9。当前实现里，超时强制放行（§5.2）与批次正常结束都会清空接收缓冲区，于是「设备还停在翻页提示上」这一状态**没有任何地方记录**。若此时超时放行或用户发起下一批命令，新命令同样会被仍在翻页的设备吃掉，与 13.9 是同一个后果，但触发路径不同：13.9 已修，这一条**未修**。

规格本身也没给出答案 —— §5.2 只要求「超时后强制放行」，§5.3 只描述翻页中如何回送空格，两者都没说「强制放行时设备仍停在翻页上该怎么办」。可行方向有三，需要**明确选定一个**再写进 §5.3：

1. 缓冲区不清空，下一条命令发出前若尾部仍是翻页提示，先回送退出键（各厂商不一致：`q` / `Ctrl-C` / 空格翻到底）；
2. 不自动处理，改为向界面抛出「设备停在翻页」事件，由用户决定（更保守，不猜厂商行为）；
3. 超时时不回送、只告警，并在给出提示前持续回送空格把剩余分页翻完。

倾向 2：厂商退出键行为尚未在真机上验证（§8.4 已列为待验证项），在没验证前让程序猜按键，风险高于让用户看见。

**使这条缺口可达的是 10s 这个默认值本身。** 一条分页输出超过 10s 的命令（设备慢、链路延迟高，`display current-configuration` 这类大输出很容易超过）必然走到「超时放行时设备仍在翻页」，然后下一条命令被吃掉。因此定方案时还应一并考虑：**命令超时是否应当在翻页期间也照常计时**（当前实现照常计时，这是 §5.3 的要求）。缺口本身能自愈 —— 设备翻完后回到真实提示符，只损失一条命令 —— 但由它造成的「用户以为执行了、实际没执行」正是最需要避免的后果。

**13.11 `close()` 不得 await 单订阅 `StreamController` 的 `close()`**

`Session` 的实现内部用单订阅 `StreamController` 把「原始字节 → 解码后的文本」接起来。**单订阅 controller 的 `close()` 返回的 Future，要等到有监听者订阅、把 done 事件取走才会完成。** 没有监听者时它永远不完成：

```
未连接会话的 close()          → 永久挂起
无监听者的 controller.close() → 永久挂起
有监听者的 controller.close() → 正常完成
```

`TelnetSession` 里 `_decodeSub` 是在 `connector.open(...)` **成功之后**才挂上去的，因此有两类会话永远没有监听者：**从未连接过的**，以及 **connect 抛过异常的**（端口写错、拒绝连接、超时）。这两类会话上调 `await close()` 会永久挂起 —— 而「连不上之后清理」「切换设备」「关窗口」走的正是这条路。FR-C-12 要求退出时关闭所有会话，挂在这里就是应用退不掉。

**约束：`close()` 里只 await 真正的资源（订阅、socket），内存 controller 的 `close()` 用 `unawaited`。** 已连接的会话 `close()` 本来正常，别为此改成 broadcast —— 那会改变 `Session.output` 的语义（多个监听者、错过早期输出）。

计划 2 的 `SshSession` 会照搬这个结构，必须一并遵守。

**13.12 对端断开时 `TelnetSession` 不释放任何资源，且丢掉了异常对象**

`sessions`（会话实现）在收到对端的 `onDone` / `onError` 时只做一件事：完成 `done` 这个 Future。socket 不关、两个订阅不取消、`_dataBytes` 与 `_output` 不关闭、`_closed` 保持 `false`。也就是说 `done` 完成之后，这个会话**仍然接受 `write()` 并静默丢弃**，并一直持有资源，直到有人调用 `close()`。

计划 1 里不成问题 —— 每个调用方都记得关（e2e 的 `_Wired.dispose`、各测试的 `tearDown`）。但**计划 2 的重连正是最容易忘记的地方**：重连会新建一个会话，旧会话的 `close()` 一旦漏掉就是一个静默泄漏。约束：**`done` 完成不等于资源已释放，`close()` 仍必须调用**；计划 2 若改为在断开时自动释放，需同时确认不影响 `close()` 的幂等性。

另一半：`onError` 的错误对象被直接丢弃，于是「连接被重置」与「主机不可达」在调用方看来完全一样。FR-C-06 要求给出可读的失败原因，计划 2 需要把错误保留下来（新增错误事件或 `lastError`），而不是在这里丢掉。

**13.13 翻页状态应当用状态标志，而不是回头嗅探缓冲区**

13.9 的修复是在 `_checkPrompt` 里排除翻页尾巴，代价是「设备是否在翻页」这一状态**每次都由缓冲区内容重新推导**。这带来两个已知的次要问题：

1. 若设备把提示符**原地覆盖**在翻页提示上（同一行、中间没有换行），`stripAnsi` 去掉 `\r` 后两者会挤进同一行，`matchesTail` 持续为真，该命令就只能等 10s 超时放行 —— 多一个多余空格，外加每条分页命令白等一次超时。此形态未在真机验证，但代价不对称，值得记下。
2. 13.9 提到的 `MorePager` 用 `contains` 匹配，因此正常输出里只要出现 `--More--` 字样就会回送一个空格（B6）。收紧成 `endsWith` 会漏掉 `---- More ---- (24%)` 这类带后缀的提示，所以**不该那么改**。

两者同一个根因：**把「我们刚回过翻页键、还在等下一页」这件事记成一个显式状态标志，在新数据到达时清除**，比每次从缓冲区重新推断更可靠，也能一并消除上面两条。（计划 2 的 `SshSession` 若也做翻页判定，应直接采用状态标志的写法。）

**13.14 `dartssh2` 4.1.0 的行为与默认值（调研结论，计划 2 必须照此写）**

版本 4.1.0 已确认可在本项目的 Dart 3.12 上解析（8 个传递依赖，无冲突），与 §8.1 的选型一致。以下每一条都会让「照着直觉写」的代码出错：

1. **没有 `connect()`，且「信任校验」默认是关的 —— 但别和「签名校验」混为一谈。**
   API 是 socket 优先：自己建好 `SSHSocket`，交给 `SSHClient(socket, username: ...)`，再 `await client.authenticated`。

   这里有两个**不同**的开关，混淆它们会写出看起来安全、实际不安全的代码：

   | 构造函数参数 | 默认值 | 管什么 | 默认是否生效 |
   |---|---|---|---|
   | `disableHostkeyVerification` | `false` | **签名校验**：证明对端确实持有它出示的那把私钥 | ✅ 默认开启 |
   | `onVerifyHostKey` | `null` | **信任校验**：这把密钥是不是我们**期望**的那把（TOFU/已知主机） | ❌ **默认形同关闭** |

   源码 `ssh_transport.dart:1919` 写得很直白：

   ```dart
   final userVerified = onVerifyHostKey != null
       ? await Future.value(onVerifyHostKey!(_hostkeyType!.name, fingerprint))
       : true;        // 回调为 null ⇒ 直接当成"已验证" ⇒ 接受任意主机密钥
   ```

   也就是说：默认配置下握手本身的密码学是健全的，但**对端是谁完全没有被检查** —— 任何持有有效密钥的中间人都能冒充目标设备。这正是 NFR-S-03 要求默认开启的那一项，而「什么都不传」等于静默关掉了它。

   **约束：`SshSession` 必须始终显式传 `onVerifyHostKey`。** 即便全局设置关闭了校验（FR-C-11 允许），也应传一个显式 `(t, f) => true` 的回调，而不是留 `null` —— 让「校验被关掉」这件事在代码里**可见、可 grep、可评审**，而不是藏在构造函数默认值里。

   `fingerprint` 参数已经是可直接显示给用户的 UTF-8 字节（形如 `SHA256:<base64>`），`utf8.decode` 之后即可展示，不需要自己再算哈希。

2. **主机密钥被拒绝，抛出的是 `SSHAuthAbortError` 且 `.reason` 为 `SSHHostkeyError`。**
   FR-C-06 要求区分「认证失败」与「协议错误」，因此**不能把这个异常和密码错误一起归为「认证失败」** —— 用户看到「认证失败」会去改密码，而真正要改的是接受指纹。

3. **`SSHSession.flush()` 不可用。**
   调用它会丢出一个未处理的异步错误，且写入内容丢失。因此 `SshSession` 对 `Session.flush()` 的实现必须是**空操作**，不能转发给 dartssh2。（`Session` 接口里保留 `flush()` 是为了 Telnet 侧，SSH 侧不适用。）

4. **`SSHSession.stdout` 是 `Stream<Uint8List>`，照抄 Telnet 的管道会在运行时报错。**
   与 §8.5 `connector.dart` 中 `_SocketConnection.input` 记录的**同一个协变陷阱**：静态类型兼容，但 `Stream.transform` 按运行时类型校验 transformer，于是 `.transform(Utf8Decoder())` 编译通过、运行时抛 `type 'Utf8Decoder' is not a subtype of type 'StreamTransformer<Uint8List, String>'`。**必须 `.cast<List<int>>()`。** Telnet 侧已经踩过并写下了注释，SSH 侧是同一条坑。

5. **`session.close()` 不完成 `session.done`，但 `client.close()` 会 —— 而 `SshSession.close()` 两个都要调。**
   实测（2026-09-24，回环 sshd，见下表）四种路径：

   | 触发方式 | `session.done` | 是否符合 `Session.done` 契约 |
   |---|---|---|
   | 我方 `session.close()` | 保持未完成 | ✅ 符合 |
   | **我方 `client.close()`（会话仍活着）** | **完成** | ❌ **违反** |
   | 对端 `exit` | 完成 | ✅ 符合（就是要的信号） |
   | 底层 socket 被销毁 | 完成 | ✅ 符合 |

   第二行是陷阱：`SshSession.close()` **必然**会调 `client.close()`，于是「主动关闭」会被 `done` 的监听者看成一次**意外断线**。后果不是少一个信号，而是**退出应用或用户主动断开时，每台设备都触发一次 FR-C-07 自动重连** —— 用户点了断开/关了窗口，工具却在拼命重连。

   **约束：`SshSession` 转发 `session.done` 时必须先查 `_closed` 标志（`if (_closed) return;`），不能直接透传。** 这与 `TelnetSession._onDisconnected` 里的写法一致。已实测该守卫**充分且必要**：带守卫时主动关闭 0 个事件、对端断开 1 个事件；去掉守卫则主动关闭也报 1 个事件。因此这一条可以直接写成一对互为反向的回归测试（主动关闭 → `done` 不完成；对端断开 → `done` 完成）。

6. **`keepAliveInterval` 默认 10 秒。**
   对 FR-C-07 的重连有直接影响：设备侧静默断开时，dartssh2 会先靠自己发现的 keepalive 失败来结束 `done`，而不是等 TCP 超时。计划 2 若要调整该值，需与 FR-C-07 的退避序列一起考虑，避免「keepalive 判定断开」与「重连退避」互相打架。

7. **`SSHForwardChannel.close()` 会挂起，必须用 `destroy()`。**（跳板机已整体放弃（§10.2），**V1 没有代码受影响**；这条从「计划 3 的前置条件」转为「V1.1 恢复跳板机时的前置条件」，先记在此处。）
   通道关闭是 `close()` 还是 `destroy()` 属于**必须显式选对**的一类 API —— 选错的表现是关连接时永久挂起，与 13.11 的症状相同但根因不同。

**13.15 FR-C-06 的错误分类必须看 `SSHAuthAbortError.reason`，不能看顶层类型或消息**

实测（2026-09-24，回环 sshd）三种失败的异常形态：

| 场景 | 抛出的异常 | `.reason` |
|---|---|---|
| 主机密钥被用户拒绝 | `SSHAuthAbortError(Connection closed before authentication)` | `SSHHostkeyError(Hostkey verification failed)` |
| **设备只提供旧算法**（`ssh-rsa`/`group14-sha1`/`aes128-cbc`/`hmac-md5`） | `SSHAuthAbortError(Connection closed before authentication)` | `SSHInternalError(Bad state: No matching key exchange algorithm)` |
| 认证失败（口令/密钥不对） | `SSHAuthFailError` | 无 `reason` 字段 |

**前两行的类型与 `toString` 完全相同。** 因此：

- 若分类逻辑看**顶层类型**或**消息文本**，则「主机密钥被拒」与「设备太旧、算法协商不了」会被归成同一类，而 §10.2 已决定 V1 不支持旧算法 —— 也就是说**用户会看到「认证失败」**，然后去反复检查一个根本没问题的口令。这正是 FR-C-06 要避免的「不可读的失败原因」。
- **唯一可靠的判据是 `.reason`**：`SSHHostkeyError` → 主机密钥问题（要提示用户去确认指纹，不是去改口令）；`SSHInternalError` → 内部/协商错误，归入「协议错误」。
- `SSHInternalError` 里的算法协商失败**只能靠消息文本**（`'No matching key exchange algorithm'`）识别。这很脆弱，因此分类器对**认不出的 `reason` 必须优雅降级**：归入「协议错误」并**附上原始消息**，而不是抛出去或吞掉。

另外要注意 `dartssh2/src/ssh_errors.dart` 里 `ssh_transport.dart:1408/1482` 抛的是**裸 `StateError`**，但它**不会**逃到调用方 —— 已被包装进 `SSHInternalError` 再放进 `reason`。所以分类器的 `catch` 仍应以 `SSHError` 为主，同时保留一个兜底分支处理非 `SSHError` 的意外异常。

对应用例（计划 2 必须覆盖）：三个场景各自的分类结果，其中**第一行与第二行必须分类不同** —— 这是这条约束的回归测试。

**13.16 测试可控性：三条实测事实（计划 2 预演中得到，含一个被否定的猜测）**

计划 2 的代码在写入计划前先抽出来编译并跑过一遍，过程中撞到下面三条。它们不是风格偏好，是**会把测试写成假测试或假失败**的坑。

1. **`fake_async` 推不动完整的「拆除」链 —— 用 `await` 串起来的 `cancel()` / `close()` 不会在 fake zone 下完成。**

   实测形态：`ConnectionManager.dispose()` → `_teardownSession()` → `await _dispatcher?.dispose()`，在 `fakeAsync` 里停在最后一步不再往下走，`session.close()` 因此**根本没被执行**，测试断言 `closed == true` 假失败。同一段代码换成真实 async，`closed` 立即为 `true`。

   关键旁证：卡住时 `async.pendingTimers.length == 0` 且 `async.microtaskCount == 0` —— **没有任何待推进的工作**，所以 `flushMicrotasks()`、`flushTimers()`、`elapse()` 都无效。这不是"少 flush 一次"的问题。

   **约束：涉及拆除（cancel / close / dispose）的断言一律用真实 `async` 测。** 拆除本身不涉及计时，真实 async 更直接也更强。`fakeAsync` 只留给**需要控制时间**的用例（退避序列、超时、断线时长）。

2. **广播 `StreamController` 的 `close()` future 并**不**等待订阅者取消 —— 这一条是为了否定一个看似合理的猜测。**

   我一度推断"`await dispatcher.dispose()` 会挂住，是因为广播 controller 的 `close()` 要等所有订阅者取消"，并据此设计了修复（先取消自己的订阅）。**实测否定了这个推断**：`StreamController.broadcast()` 在「有活跃订阅者」「无订阅者」「订阅者已取消」「单订阅 controller」四种情形下，`close()` 的 future 都**立即完成**（`package:fake_async` 内外都一样）。

   所以第 1 条的成因**尚未定位**（已排除：订阅者数量、订阅者取消、zone 一致性、嵌套 async 层数、dispatcher 单独调用）。**不要在没重新实测的情况下把它归因到 broadcast 语义上。**

   但由此得到的**设计结论仍然成立**：`session.close()` 不该挂在 `dispatcher.dispose()` 的 future 后面 —— 订阅 `dispatcher.events` 的不止 `ConnectionManager`（界面也会直接订阅），让 FR-C-12 依赖一个我们控制不了的 future 是错的。`dispose()` 的**同步**部分（`_disposed = true`、清空队列）立即生效，fire-and-forget 足以保证"不再发出任何命令"。

3. **`Uint8List` 的 `runtimeType` 与类型字面量 `Uint8List` 不 `==`。**

   `expect(value.runtimeType, Uint8List)` 会失败，且失败信息是 `Expected: Uint8List, Actual: Uint8List` —— 极具误导性（实测：`seen == Uint8List` 为 `false`，`identical(seen, Uint8List)` 也为 `false`，而 `value.runtimeType.toString()` 打印出来就是 `Uint8List`）。

   **约束：断言类型一律用 `expect(value, isA<T>())`，永不用 `expect(value.runtimeType, T)`。**

4. **时间源必须用 `clock.now()`（`package:clock`），不能用 `DateTime.now()`。**

   `fake_async` 推进的是 `clock`；`DateTime.now()` 走真实时间。用后者的话，测试里 `elapse(1s)` 之后算出来的时长恒为 0 秒，FR-C-09 的「断线时长」永远断言不了（实测：`fakeAsync` 里 `elapse(7s)` 后 `clock.now()` 恰好前进 7s）。

   `clock` 通常已在传递依赖里，但**必须**在 `pubspec.yaml` 里显式声明为直接依赖才能 `import`。

### 13.17 `ConnectionManager` 的三处实测结论（计划 2 执行期）

1. **用户主动断开时，状态必须是 `disconnected`（灰），不是 `failed`（红）—— 而 `_userClosed` 必须同时守住失败分支。**

   §5.4 的表格写的是「用户主动断开 → 停止重连，按钮变灰」。但只把 `disconnect()` 里的状态设对是不够的：用户在 `session.connect()` **还没返回**时点"断开"，`disconnect()` 会关掉 socket，于是那个在途的 connect **抛错**并走进 `_attemptConnect` 的 catch 分支。

   若 catch 只判断 `_disposed`（而成功分支判断的是 `_disposed || _userClosed` —— 这个不对称就是漏洞本身），后果有两层：
   - 发出一条**假告警**：这次失败是我们自己关 socket 造成的，设备没有任何问题；
   - 经 `_scheduleRetry()` 把状态刷成 `failed`，按钮**从灰变红**。

   实测证据（修复前）：`Expected: DeviceConnectionState.disconnected, Actual: DeviceConnectionState.failed`。

   **约束：`_attemptConnect` 的 catch 与 `_scheduleRetry` 都要在 `_userClosed` 时早退；`failed` 只留给 `!autoReconnect` 这一种情形，两者不可合并判断。**

2. **`CommandDispatcher.events` 是异步广播流，因此「转发订阅」是死代码 —— 一个看似成立的重复发送推断被证伪。**

   代码评审曾判断 `ConnectionManager` 里那个 `_dispatcherSub` 转发订阅（收到 `QueueDropped` 就 `_events.add(SessionLost(null))`）会导致**一次断线发出两个 `SessionLost`**：一个来自 `_onSessionDone`，一个来自转发。**实测不成立** —— 把那段代码原样放回去，断言 `lost.length == 1` 的测试**仍然全绿**。

   原因：`CommandDispatcher._events` 是 `StreamController.broadcast()`（**没有** `sync: true`，见 `command_dispatcher.dart:100`），`onDisconnected()` 投递的 `QueueDropped` 要等一个 microtask 才送达；而 `_onSessionDone` 在下一行就调用 `_teardownSession()`，后者在**同一个同步块**内取消 `_dispatcherSub`。转发监听器永远等不到那条事件。

   所以那段转发**从未触发过**，是死代码，而不是重复发送。删除它的理由因此是"它达不到注释宣称的效果"，不是"它会重复发送"。

   **同时要记住这条结论是顺序敏感的**：把 `_teardownSession()` 里那行 `cancel()` 挪到 `await outputSub?.cancel()` **之后**，转发就会收到事件、测试立刻变红（`expected 1, actual 2`）。所以约束的正确形态是**"不要订阅 `dispatcher.events` 去转发"**，而不是"记得及时取消订阅" —— 后者把正确性押在两行代码的先后顺序上。

   **约束：丢弃数（FR-C-10 的告警）由 `QueueDropped` 承载，界面直接订阅 `dispatcher.events` 取用（见 §13.16 第 2 条的设计结论），`ConnectionManager` 不转发命令队列的任何事件。** 另：**不要**再依据"广播流的 close/取消顺序"推断同类问题 —— 先测。这一节的第 2 条与 §13.16 的第 2 条是同一类教训。

3. **`failed`（红）在产品里何时可达 —— 已决策（2026-09-26）：首次失败即变红，之后再退避。**

   FR-C-06 要求「连接失败时，设备按钮变红」，但 `ConnectionManager` 的 `autoReconnect` 默认 `true`，且没有任何生产代码传 `false`（只有测试传过），于是 `failed` 在改动前在实际产品里**永远到不了**。这是 FR-D-09 与 §5.4 两处口径不一致的外显：

   - FR-D-09 概述为「红=连接失败**或已断开**」；
   - §5.4 的逐事件表却是：检测到断开→**黄**、重连失败→**维持黄**、用户主动断开→**灰** —— 表里**没有红**，也没为「首次建连就失败」留一行。

   计划 2 当时暂按第 1 种读法实现（与更具体的 §5.4 逐事件表一致）。**2026-09-26 拍板改按第 2 种读法**：

   1. ~~首次建连失败也走退避重连（黄），`failed` 仅留给 `autoReconnect == false`~~ —— **原读法，已废弃**。
   2. **首次建连失败立即变红（照 FR-C-06 字面），随后若要自动重连再转黄。** 落点：`_scheduleRetry` 在 `_attempt == 0` 时置 `failed`，之后才走退避；`_attemptConnect` 开头按 `_attempt` 是否为 0 选 `connecting` / `reconnecting`。由计划 5b-2 的 Task 12 落地。

   **`failed` 的含义随之改变**：不再是「不再自动重试」，而是「**这一次尝试失败了**」——`DeviceConnectionState.failed` 的文档已同步更正，**别再照着旧文档推理**。

   另：`autoReconnect` 开关在 spec 里仍然**没有依据** —— FR-G-01 的设置项列表里没有「自动重连」，而 FR-C-07 又要求断线后必须自动重试。它今天只是「关掉自动重连」的**测试注入点**，生产路径一处都不传。**这一条仍未决**（要么给 FR-G-01 加一项，要么删掉这个参数），但它已不再是红的可达性问题，所以不阻塞 5b-2。

   **计划 2 的 Task 6 实现之前必须定下来。** 计划文件里同一项记在「未决项」一节。

### 13.18 `ConnectionSocket` 的三处实测结论（计划 2 Task 1 执行期）

1. **`sink` 必须是同步 controller，否则"写出去后立刻关闭"的字节会被静默丢弃 —— SSH 的优雅关闭报文就是这样丢的。**

   `SSHSocket.sink` 在本项目里由适配器自己用一个 `StreamController` 承接。**默认（异步）controller 会让 `sink.add` 推迟一个 microtask 才调用 `Connection.write`，而 `Connection.close()` 的关闭标记是同步置上的** —— 于是同一个同步块里"先写、后关"的字节，落到 `_SocketConnection.write` 时连接已标记关闭，被直接丢掉，不报任何错。

   实测（真 sshd + 真 `SSHClient`，通过一个记录调用顺序的 `Connection` 包装层观察）：

   | 场景 | 对端实际收到的字节 |
   |---|---|
   | 裸 `dart:io` Socket：`add([1,2,3])` 后同步 `close()` | `[1, 2, 3]` |
   | 适配器（异步 sink）：同上一个同步块 | **`[]`** |
   | 适配器：`add` 后让出一个 microtask 再 `close()` | `[1, 2, 3]` |

   在 `Connection` 上看到的调用顺序是 `[close, write-DROPPED(36B), write-DROPPED(36B)]` ——
   即 `SSHClient.close()` → `_closeChannels()` → `SSHChannelController.destroy()` →
   `_sendEOFIfNeeded()` / `_sendCloseIfNeeded()` → `socket.sink.add(...)`，全是同步调用，
   紧接在 `await _transport.close()` → `socket.close()` 之前。**`CHANNEL_EOF` 与
   `CHANNEL_CLOSE` 因此从未上线**，而裸 socket 路径下它们是发出去的 —— 也就是说这层
   适配器把一个原本正确的行为改坏了。

   **代价要说准，别说过头**：**TCP 连接仍然会正常关闭** —— `close()` → `_conn.close()`
   → socket 发出 FIN，设备侧的会话不会因此挂住。丢掉的是 **SSH 协议层的优雅关闭**
   （`CHANNEL_EOF` / `CHANNEL_CLOSE` / 可能的 `DISCONNECT`），影响的是协议卫生：对端
   日志里的 teardown 与 channel 状态机会看到一次不完整关闭。

   **不要写成"vty 会被一直占住、要 `clear line vty`"** —— 那是 TCP 连接从未关闭
   （客户端崩溃、链路中断）才有的现象，本情形不是。这一条曾按直觉写进 spec，属于
   "推断冒充实测"，经评审指出后改掉；本节的规矩是**先测**。

   **修法**：`StreamController<List<int>>(sync: true)`。加 `sync: true` 后重测：
   `[write(36B), write(36B), close]`，两个报文都发出去了。

   **副带影响（三条"看起来像、实测不是"的直觉，一并记下，免得下次有人照着改）**：

   - `Connection.write` 若同步抛错，**并不会**从 `sink.add` 里抛出来。实测
     `try { sink.add(...) } catch (e) { … }` 什么都捕不到（`escaped == null`）：
     错误经 `_BufferingStreamSubscription._sendData` → `_RootZone.runUnaryGuarded`
     仍然变成未捕获的 zone 错误，**落点与异步 controller 完全相同**，只是上报时机
     从下一个 microtask 提前到同步。所以别指望 `try/catch` 包住 `sink.add` 能接住
     写入失败。
   - 同步 controller 的监听回调里**重入 `add` 不会抛 `StateError`**。Dart 3.12 的
     `stream_controller.dart` 里根本没有 `_isFiring` / `Cannot fire new event` 这类
     守卫，实测重入 add 正常通过。别拿这个当"不能重入"的理由。
   - `dispose()`（即 `_sink.close()`）之后再 `sink.add` 会同步抛
     `Bad state: Cannot add event after closing`。这条**不是** `sync: true` 带来的：
     异步 controller 抛的是一模一样的错误，因为 `_StreamController.add` 在两条派发
     路径之前就查了 `_mayAddEvent`。

   **`_sink` 上那条 `onError` 是不可达的**：`Connection.write` 是同步 `void`，没有错误
   通道；而 `onData` 里抛出的异常**不会**路由到同一个订阅的 `onError`（实测：它会变成
   未捕获的 zone 错误）。留着它只为满足 `StreamSink` 的契约形态，别指望它兜住写入失败。

2. **`dispose()` 不关闭底层 `Connection`，且刻意返回 `void`。**

   `Connection` 是从调用方借来的，生命周期归调用方（计划 2 的 `SshSession.close()` 是
   先 `client.close()` 再 `dispose()`）。`dispose()` 只释放适配器自己的两个订阅。

   返回 `void` 而非 `Future<void>` 是**刻意的**：`dispose()` 里对两个 controller 的
   `close()` 只能 `unawaited` —— 单订阅 controller 的 `close()` Future 要等有监听者
   取走 `done` 才完成，无人监听时永久挂起（§13.11）。如果签名是 `Future<void>`，将来
   有人"顺手"把它改成 `await _stream.close()` 就会让 `dispose()` 永不返回；`void`
   让那个 await 根本写不出来。**不要把签名改成 `Future<void>`**，除非同时想清楚
   §13.11 那条挂起路径怎么防。

3. **给跳板机计划的两条前置条件 —— 计划已取消（2026-09-25），转为 V1.1 的前置条件。**
   （下面「计划 3」一律读作「将来恢复跳板机的那个计划」。V1 没有隧道化的
   `Connection`，所以两条在 V1 里都**没有触发路径**，写在这里是为了不让它们丢失。）

   - `SSHSocket.destroy()` 在本适配器里退化成 `_conn.close()`（`Connection` 没有
     destroy 的等价物），而 `SSHTransport.close()` 是 `await socket.close()` →
     `await _conn.close()`。**于是任何 `close()` 可能挂起的 `Connection` 都会把拆除
     流程挂住，`destroy()` 这条"立刻走开"的路径也一并继承。** §13.14-7 已记录
     `SSHForwardChannel.close()` 会挂起 —— 所以计划 3 里隧道化的那个 `Connection`
     必须让它的 `close()` 具备 `destroy()` 语义（走 `SSHForwardChannel.destroy()`），
     否则 FR-C-12「退出时关闭所有会话」会卡死。
   - `done` 的完成**依赖对端真的结束 `Connection.input`**。这一点对
     `_SocketConnection` 实测成立（`close()` 与 `destroy()` 之后 `done` 都会完成），
     但它是 `Connection` 实现方的**隐含前提**：计划 3 的隧道 Connection 关掉内层
     channel 时必须让 `input` 结束，否则 `SshSession` 的 `done` 永远不会完成。

### 13.19 `ConnectionFailure` 的实测结论（计划 2 Task 3 执行期）

1. **`_classify` 里每一支的 `cause:` 都是死参数 —— 但只在一条路径上看得出来。**

   `classifyConnectionFailure` 先算 `final inner = _classify(error);`，再用
   `cause: error` 重建（hop 分支同样）。于是 `_classify` 里每一处 `cause:`
   传入的值**无一被观察**（写这段时是 9 处；Task 3 的修复轮又加了两支，
   现为 12 处，全文件 15 处 —— 计数变了，结论没变）。行为上不算错：最终 `cause` 恒为最外层
   异常，与文档「原始异常对象」一致（用户拿到的"原始"就是 `connect()` 真正
   抛出的那个）。

   实测（2026-09-24，本机）：把该行改成 `cause: inner.cause`，**26 个用例全绿**
   （写下这条时全文件 14 条，后续补到 26 条后**重跑仍是全绿** —— 结论没变；
   计数会变，见第 10 条的方法论教训）。
   原因是绝大多数分支里 `inner.cause` 与 `error` **本就是同一个对象**，改与不改
   没有区别 —— 真正会分叉的**只有 `SSHSocketError` 的拆包路径**：那里
   `inner` 来自递归 `_classify(error.error)`，`inner.cause` 是内层 `SocketException`
   / `TimeoutException`，而 `error` 是外层包装对象。

   **残留（已接受，不在计划 2 修）：** 这条路径上的 `cause` 没有任何用例钉住 ——
   现有用例对拆包路径只断言 `kind`。于是「给日志用的 `cause` 到底是什么」在
   **唯一会分叉的那条路径上**是没被锁的。计划 4/5 若打算把 `cause` 展示成
   "详细信息"，先确认这里给的是不是界面要的东西。

   **给将来动手的人：** 若因为第 1 条去清理 `_classify` 里那些死 `cause:`，
   必须**同时**补上钉住 `cause` 的用例；
   否则这次改动对十二条路径里的十一条是静默的（十二条里只有 `SSHSocketError`
   的拆包路径会分叉，而它同样没被钉住）。

2. **`SSHInternalError` 的文案不得断言成因（已修正）。**

   dartssh2 对这个类的自述是"不该发生的错误，多半是库自身的缺陷"
   （`ssh_errors.dart:14-16`），算法协商失败只是它承载的**其中**一种。原文案
   「与该设备协商加密参数失败」会把一个库缺陷说成设备的算法问题 —— 用户跑去翻
   设备的 SSH 配置，而那正是 §13.15 要避免的「指向错误的东西」。现文案并列两种
   可能，并附上 `reason.error` 原文。

3. **两条分支曾经是零覆盖的（已修正，留作教训）。**

   §13.15 要求的「优雅降级」与 `SSHSocketError` 的拆包，最初各有一条用例，
   但把分支体换成 `throw` 之后**12 个用例照绿**（当时全文件 12 条；这两个洞
   补上用例后现为 26 条 —— 计数是历史值，别拿去复现）—— 前者因为传进去的 `reason`
   是**认得出的** `SSHInternalError`（根本没走到兜底），后者则完全没有用例碰。
   两条都是「代码在、约束不在」。现在各有用例，且已用变异证明会变红。

   **教训：**「这条需求有对应代码」不等于「这条需求被测试约束」。§13.15 这类
   **降级/兜底**分支尤其容易写成"看起来覆盖了" —— 因为要让它们变红，输入必须
   真的是**认不出的**那一种。

4. **`kind` 被钉住了，文案没有 —— 而 FR-C-06 的交付物就是文案。**

   规范符合性评审发现，把主机密钥那条消息整段换成「认证失败：用户名、口令或
   私钥不正确」，**14 条用例全绿**（实测）：`kind` 仍是 `hostKey`，没有任何断言
   看文案。于是用户可以拿到一个分类正确、却把他指向口令的消息 —— **正是 §13.15
   存在的唯一理由**。同类漏洞还有两个，同样全绿：整支删掉
   `is SSHInternalError`（兜底返回的 kind 一样，只有文案退化）、整支删掉
   `is SSHError`（`SSHStateError` 掉进 `unknown`，而 §13.15 明说 unknown 只留给
   非 `SSHError` 的意外）。

   已补三条用例，钉的是「文案把人指向哪里」而不是逐字文本（`contains('指纹')`、
   `isNot(contains('口令'))`）：这样改措辞不会误报，改**方向**才会。

   **教训：**分类器的测试如果只断言 `kind`，那它测的是"我们分对了类"，不是
   "用户看懂了"。

5. **三条「字面上没错、但可能不是用户想要的」路径（评审提出，未改代码）。**

   - **跳板机上下文会盖掉 §13.15 的区分。** `hop != null` 时 kind 一律是
     `jumpHostFailed`，于是「主机密钥被拒」与「算法协商失败」在带 hop 时 kind
     相同 —— §13.15 那条"两者必须分类不同"的回归测试此时不成立。这是**有意**
     的（FR-J-05 要求先告诉用户哪一跳失败，实现里有注释说明），且 message 仍带着
     内层原因（「第 1 跳 X 失败：主机密钥校验未通过：…」），用户仍被指向指纹。
     但要注意：**若计划 5 的界面按 kind 决定颜色/图标，跳板机上的主机密钥问题就
     失去它的专属外观了** —— §13.17-3 定颜色口径时要一并考虑。

     **2026-09-25 补充：**跳板机已整体放弃（§10.2），生产路径上 `hop` **恒为 null**，
     所以上面这条冲突在 V1 里**不可达**。剩下的要求是**反向的**：计划 5 的颜色/图标
     口径里**不要**为 `jumpHostFailed` 设计专属外观 —— 今天没有任何代码路径能产出它，
     做了就是一条不可测的死分支。
   - **裸 `SSHHostkeyError` 不算主机密钥问题。** `classifyConnectionFailure(
     SSHHostkeyError(...))` → `protocolError`，用户不会被提示去确认指纹。连接
     路径上它总被包进 `SSHAuthAbortError`，所以**现在**够不到；但**活会话**上
     （rekey 时密钥变了，`ssh_transport.dart:1901/1925`）它是裸的，而 §13.12 要求
     会话级错误也要报给用户 —— 即 **§13.20 一修好，这条路径就通了**。
     建议 §13.20 落地时一并决定：给顶层 `SSHHostkeyError` 也加一支，还是在
     §13.20 的用例里写明"它归 protocolError"是接受的。
   - **`SSHSocketError` 嵌在 `.reason` 里时不拆包。** 顶层会拆（→ `unreachable` /
     `timeout`），但 `SSHAuthAbortError(..., SSHSocketError(SocketException(...)))`
     落到兜底 → `protocolError`，而 §13.12 点名了「连接被重置」这个场景。
     §13.15 的字面要求是"认不出的 `reason` 优雅降级"，所以这**不算违规**；记在
     这里是因为同一类输入在两条路径上得到不同的精度，将来读代码的人会疑惑。

6. **`ConnectionFailureKind.timeout` 曾是死代码，而它的注释写着"FR-C-13"
   （评审提出，已修）。** 这是本 Task 最严重的一个，因为出错的不是实现，
   而是**计划的整个前提**：「`Socket.connect` 带 timeout 会抛 `TimeoutException`」
   —— 这句话没有人量过。

   - **实测：** `Socket.connect('192.0.2.1', 22, timeout: Duration(seconds: 2))`
     抛的是 `SocketException`，`osError.errorCode == 110`（POSIX `ETIMEDOUT`），
     消息为 `Connection timed out` —— **不是** `TimeoutException`。两个黑洞地址
     （`192.0.2.1`、`10.255.255.1`）结果一致。
   - **后果：** FR-C-13 的 15s 超时 —— 本程序**最常见**的失败 —— 被归成
     `unreachable`，并把英文原文塞进 `message`，而该字段的文档写着
     "可直接展示给用户的中文说明"。同时 `timeout` 这个 kind 成了
     **带活注释的死代码**：文档断言"连接超时（FR-C-13，默认 15s）"，
     却没有任何生产输入能产生它。
   - **为什么没有测试拦住：** 名为「连接超时」的那条用例喂的是手搓的
     `TimeoutException` —— 一个生产路径**不会抛**的形态。用例绿着，被测的
     行为是错的。这类"绿得毫无意义"比红更难发现。
   - **修法（已落地）：** 在 `SocketException` 分支里判 errno，同时认 POSIX
     `110` 与 Windows `10060`（`WSAETIMEDOUT`）。放在分类器里而不是
     `DirectConnector` 里，是因为 socket 错误也会从 dartssh2 的传输层以
     `SSHSocketError` 形式冒出来，只在 connector 翻译会漏掉那条路径。
     110 为本机实测；**10060 取自 Winsock 文档值，本机（Linux）无法实测** ——
     这一点已写进代码注释，没有伪装成实测。
   - **教训：**与第 4 条同源但更狠。第 4 条是"断言不够"，这条是"计划里的前提
     本身没量过"。凡是要写进计划的「某库在某场景会抛 X」，都要先用一段最小
     程序验一次 —— 这也正是 §13.15 当初被发现的同一种方法。

7. **带口令的 OPENSSH 私钥会漏出 `null` 和英文类名（评审提出，已修）。**
   `SSHKeyPair.fromPem(pem)` 不带 passphrase，所以带口令的私钥都会失败，
   落到 `is SSHError` 兜底，产出：
   `协议错误：SSHKeyDecryptError(Private key is encrypted, null)` ——
   一个英文类名、一个字面 `null`，以及一个错误的方向（说成协议问题，用户会去
   翻算法配置）。修法：在 `is SSHError` **之前**插一支 `is SSHKeyDecodeError`，
   归 `authFailed` 并给出中文文案。`SSHKeyDecryptError extends SSHKeyDecodeError`，
   一支覆盖两者。
   **顺序是这个修法的全部要点** —— 排到 `is SSHError` 之后就等于没写：
   编译器不报错，测试也不会红。
   **订正（复审时补测）。** 这条原先写的是「**任何**设了口令的私钥都会失败并
   落到兜底」—— 错的。实测里只有带口令的 **OPENSSH** 私钥抛 `SSHKeyDecryptError`；
   带口令的 **PKCS#1** 抛 `ArgumentError`，本分类器没有哪一支接得住它，最终落在
   `unknown`（见第 9 条形态表）。一条注释把"我测过的那一种"写成了"全部"，
   而第 9 条存在的理由正是这个。

8. **两条"守文案"的纪律此前只被单向覆盖（评审提出，已修）。**

   - **方向只钉了一半。** 第 4 条证明了「主机密钥的文案不能指向口令」，但**镜像
     没测**：把 `authFailed` 的文案换成主机密钥那一句，改动前全绿（实测）。
     同样是"把人指向错误的方向"，后果是用户去核对指纹、甚至怀疑遇到中间人。
     已补一条对称用例。
   - **覆盖面声明大于实际覆盖面。** 名为「每种 kind 都有非空的中文说明」的用例
     只喂了 4 个输入，而枚举有 7 个成员 —— `hostKey` / `protocolError` /
     `jumpHostFailed` 三类的文案**零覆盖**（整段换成 `'null'` 也全绿）。
     已改成覆盖七个 kind，并用 `ConnectionFailureKind.values` 断言"一个都不能少"，
     这样将来加成员时该用例会自己红，而不是悄悄落后。

9. **`fromPem` 的失败有七种形态，分类器一种都认不出 —— 洞在调用点，已指派
   给 Task 4（评审提出，待修）。** §13.19-7 补上的是 `SSHKeyDecodeError` 那一支，
   但真正会抛出来的东西比它多。在 dartssh2 4.1.0 上实测（2026-09-24）：

   | 用户的真实操作 | 抛出 | 现分类 | 用户看到 |
   |---|---|---|---|
   | 选了一个公钥文件 | `UnsupportedError`（`Unsupported key type: PUBLIC KEY`） | `unknown` | `连接失败：Unsupported operation: …` |
   | 选了一个 PKCS#8 加密私钥 | `UnsupportedError`（尾部 `ENCRYPTED PRIVATE KEY`） | `unknown` | 同上 |
   | **选了明文 PKCS#8 私钥**（`-----BEGIN PRIVATE KEY-----`，`openssl genpkey` 的默认输出） | `UnsupportedError('Unsupported key type: PRIVATE KEY')` | `unknown` | 同上 |
   | 选了非 PEM 文件 / `ssh-rsa AAAA… user@host` 一行式 / base64 损坏 | `FormatException` | `unknown` | `连接失败：FormatException: PEM header must start with -----BEGIN `（base64 损坏还会把多行 caret 块倒进输出区） |
   | 截断或损坏的 OPENSSH 私钥 | `SSHPacketError` | `protocolError` | `协议错误：SSHPacketError(Malformed packet: …)` ← **方向指错** |
   | 带口令的 **PKCS#1** 私钥（`Proc-Type: 4,ENCRYPTED`） | `ArgumentError('passphrase is required for encrypted key')` | `unknown` | `连接失败：Invalid argument(s): passphrase is required for encrypted key` |
   | **私钥路径写错 / 文件不可读** | `PathNotFoundException`（`FileSystemException` 的子类，来自 `File(path).readAsStringSync()`，**不是** `fromPem`） | `unknown` | `连接失败：PathNotFoundException: Cannot open file, path = …` |

   「路径写错」那一行是最可能发生的输入，而「截断或损坏的 OPENSSH 私钥」那一行
   正是 §13.19-2 要防的那种误导：
   用户会去查算法，实际是他的密钥文件坏了。

   **订正（复审时逐条补测）。** 这张表最初只有五行，且第五行写的是
   `FileSystemException` —— 用户实际看到的是它的**子类** `PathNotFoundException`。
   补上的两行里，**明文 PKCS#8 那一行最要紧**：`openssl genpkey` / `req -newkey`
   的默认输出正是这个格式，也就是**一个完全正确、无口令的私钥同样会失败**，
   而它的失败原因与"格式本版本不支持"挤在同一个 `UnsupportedError` 里。
   所以 Task 4 的文案不能只说"私钥格式不支持"，要能分开
   「你选的是公钥」「这个格式本版本不支持」。

   **这张表未必穷尽。** 它是照着实测输入列的，不是照着 `fromPem` 的分支列的；
   每多测一种输入就可能多一行。别把它当封闭集合用 —— 判据是"调用点要把
   **全部**异常翻译掉"，不是"覆盖表里这七种"。

   **修法不在分类器里。** 分类器只拿到一个裸 `Object`，无从知道这个
   `FormatException` / `UnsupportedError` / `SSHPacketError` 来自"读私钥" ——
   在分类器里按这些类型做全局映射，会冤枉其它同样抛它们的来源。上下文在
   **调用点**：`SshSession._identities()` 知道自己在加载私钥，就该在那里把
   **全部**异常翻译成一个带中文说明的 `ConnectionFailure` 再抛。

   **落地时预演发现的两种偷懒写法（Task 4 fence 已按此定稿）。**"在调用点翻译"
   对 `SSHKeyDecryptError` 有两个看起来合理的替代，两种都会把洞放回来：

   - **改成 `rethrow` 放行给分类器**（理由是"分类器认得它"）。后果是
     `connect()` 不再满足"本地密钥问题必然抛 `ConnectionFailure`"，用户看到
     什么就取决于调用方有没有记得分类 —— 而 §13.19-7 的 `null` 泄漏正是这样
     一层一层漏过去的。
   - **不单独设支，让它落进兜底 `catch`。** `SSHKeyDecryptError` 的 `error`
     字段**就是 `null`**，它会连同英文类名一起被拼进消息：§13.19-7 修好的
     缺陷换一层原样复活，而 Task 3 的用例**照绿**（它们直接测分类器，
     不经过 `_identities()`）。

   判据记在这里：**`connect()` 不该为本地密钥问题漏出非 `ConnectionFailure`
   的异常。** 这条不变量同时排除上面两种写法。

   为此分类器新增了幂等分支（`if (error is ConnectionFailure) return error;`），
   否则那个对象会被再包一层，变成「连接失败：ConnectionFailure(authFailed): …」。
   **Task 4 的 fence 与用例必须覆盖这一点**，尤其是"路径写错"那条最可能的输入。

10. **幂等分支漏了递归入口（复审提出，已修）。** 幂等只在
    `classifyConnectionFailure` 顶部判，而 `_classify` 里 `is SSHSocketError`
    那一支会**递归**回 `_classify(error.error)` —— 那次递归不经过顶部。于是
    `classifyConnectionFailure(SSHSocketError(ConnectionFailure(authFailed, …)))`
    得到 `unknown`，消息是
    `连接失败：ConnectionFailure(authFailed): …`：正是幂等分支要防的双层面具，
    只不过这次是分类器自己造的。修法是在 `_classify` 顶部自己再判一次。

    实测（2026-09-24）：删掉 `_classify` 顶部那一行，**只有**新补的那条用例红
    （1 红、0 假红，且红的是用例名而非文件名）；而删掉
    `classifyConnectionFailure` 顶部那一整块（第 12 条变异）时，同一组里的
    递归用例**照样绿** —— 红的是同组那条 `same(original)`。所以第 12 条的红色
    **不构成**对 `_classify` 那一行的覆盖，两处必须各有一条用例。
    教训：**任何"回到自己"的分支都要自己重新判一次前置条件**，这类洞不写用例就永远发现不了。

    **附带的方法论教训：变异表的结论会随实现一起过期。** 补上这一行之前，
    第 12 条变异（删顶部整块）会红**两**条用例，其中一条靠的是
    `isNot(contains('连接失败：'))`；补上之后只红**一**条（`same(original)`），
    那条 `isNot` 断言在没有任何单点变异能让它红的状态下活着。变异表的每一行都
    记着"哪条用例挡住了这个缺陷"，**实现一改，这个对应关系就可能失效**，
    而失效是无声的（表还挂在那里，读的人以为它验过）。所以**改完实现要重跑整张表**，
    不是只跑受影响的那几行。

11. **文案里的每一段都有"被删掉而没人发现"的风险（复审提出，已修）。** 第 3 条记的
    是"分支体零覆盖"；这是它的**下一层**：分支在、用例也在，但用例只断言了 `kind`
    或文案里的某一个词，于是**文案其余部分被删光也全绿**。复审一次找出**七处**，
    我逐条实测复现，**全部**是全绿（当时 26 条）：

      · 跳板机包装里的 `：${inner.message}` —— 删掉后用户只看到"第 1 跳 X 失败"，

    另有一处是**另一种**缺陷（原复审的 F8，nit）：超时文案当时在

### 13.20 断开原因到不了界面（计划 2 执行期发现，Task 6 之前必须修）

§13.12 要求把会话断开的错误对象保留下来。计划 2 的做法是在 `SshSession` 上加了
`lastError` —— 但**这个字段没有任何人读**，而且它不在 `Session` 接口上。

证据链：

- `Session` 接口（`lib/connection/session.dart`）只有 `output` / `done` /
  `connect` / `write` / `close`，**没有** `lastError`。`ConnectionManager` 只认
  `Session` 这个类型，因此够不着它。
- `ConnectionManager` 于是改用 `session.done.then(..., onError: (e) => ...)` 取错误。
- 但 `done` **永远不以错误完成**：`TelnetSession._onDisconnected([Object? _])`
  把形参写成 `_` 直接丢掉，`SshSession._onDisconnected` 则存进 `_lastError` 后
  同样 `_done.complete()`（不带参数）。
- 结果：`onError` 分支永不执行 → `SessionLost(null)` 恒成立 → **失败原因一次都
  没到过界面**。

也就是说 §13.12 描述的症状（「连接被重置」与「主机不可达」在调用方看来完全一样）
并没有被消除，只是上移了一层：错误被保留了，但没有出口。

**修法（计划文件的「未决项」一节有完整步骤）：** 把 `lastError` 提升为 `Session`
的**抽象**成员（不要默认 `=> null` —— 默认值会让新实现静默返回 null），
`TelnetSession` 补上，Task 6 改读 `session.lastError` 并删掉那条死的 `onError`
分支。

**为什么不让 `done` 以错误完成：** 那样每个 `await done` 的人都得处理它，而断开
原因是诊断信息、不是控制流信号；无人监听的 `completeError` 还会变成未捕获的
异步错误。§13.12 给的正是这两个选项（「新增错误事件或 `lastError`」）。

**为什么这条重要：** Task 6 的单测会照常通过 —— 它断言的是 `SessionLost` **事件
发出来了**，不是它**带了什么**。所以这个缺陷不会在测试里露头，只会在产品里表现
为"断线了，但不知道为什么"。

### 13.21 `SshSession` 的四条残留（计划 2 Task 4 执行期，2026-09-25）

Task 4 经两轮评审后通过。以下四条是评审查出、但**故意没有在 Task 4 修掉**的项 ——
写在这里是为了让它们带着证据和结论继续走，而不是在交接时蒸发。

#### 1. 连接超时只管拨号，拨通之后没有上限（**Task 6 之前必须定**）

`SshSession.connect()` 把 `connectTimeout` 只交给了拨号：

- `connector.open(..., timeout: connectTimeout)`（`ssh_session.dart:185`）
- 之后 `await client.authenticated`（`:206`）与 `await client.shell(...)`（`:215`）
  **没有任何超时**。

`handshakeTimeout` / `authTimeout` 在 dartssh2 里默认都是 `null`，而 `lib/` 下没有
任何一处设过它们（Task 3 的注释已记录，见 §13.19 与 `connection_failure.dart` 里
`TimeoutException` 那一支的说明）。

**后果：** 一台**接受了 TCP 却不说话**的设备（老设备卡在 KEX、或中间有只做 TCP
代理的黑洞设备）会让 `await client.authenticated` 永远挂着 —— 按钮一直黄，既没有
`ConnectionFailed`、也不重连。FR-C-13 承诺的是「连接超时默认 15 秒」，用户看到的
却是无限等待。**这不是「慢」，是没有任何出口。**

**为什么当时没修：** 计划明写「**FR-C-13 的 15s 超时走的是这里，不是
`TimeoutException`**」（计划 1629 行），且提前警告：谁要给 `SSHClient` 设
`handshakeTimeout`，超时会变成 `SSHHandshakeError('Handshake timed out')` → 落进
`is SSHHandshakeError` 那一支 → 报成 `protocolError`，**把方向指到算法上去**
（计划 1546—1549 行）。也就是说「拨号之外也设超时」必须先给 Task 3 那个**已冻结、
字节校验过**的分类器补一支 —— 修它会解冻 Task 3 并要重跑它那张 24 行的变异表。
这个代价不该在 Task 4 的收尾里顺手付掉。

**推荐的修法（便宜且不动 Task 3）：** 在 `SshSession` 这一层给拨号之后的阶段包一个
`.timeout(connectTimeout)`，让超时以 `TimeoutException` 抛出 —— 而
`TimeoutException` → `timeout` 这一支在 Task 3 里**早就写好、也测过了**
（`_timeoutMessage`）。顺带说明：Task 3 那条注释把 `TimeoutException` 这一支称作
「防御性的、今天不可达」—— 一旦这样修，它就有了第一个真实调用方，**那条注释要
一起订正**（注释改动不影响任何用例，但按「实现一改就重跑整表」的规矩仍应重跑一遍
确认）。

**替代方案（不推荐）：** 设 dartssh2 的 `handshakeTimeout`。它会把超时错误塞进
`protocolError` 方向，且同样要动 Task 3。

#### 2. `TelnetSession.connect()` 没有入口守卫（与 `SshSession` 行为不一致）

`SshSession` 现在有一个**拨号之前**的入口守卫（`if (_closed) return;`），所以
「已经 close 过的会话再去 connect」不会碰网络（Task 4 有对应用例，断言
`connector.openCount == 0`）。

`TelnetSession.connect()`（`telnet_session.dart:41`）**先拨号，再判 `_closed`**：
守卫在 `connector.open(...)` **之后**。同一个情形下 Telnet 会真的去连设备，拿到
连接再关掉。两种会话对同一件事有两种行为，而这条差异没有用例钉住。

**修法：** 给 `TelnetSession` 补上同样的入口守卫（把 `if (_closed) return;` 提到
`connector.open` 之前），并补一条与 `SshSession` 对称的用例。属于计划 3 或计划 5
的顺手项。

#### 3. 主机密钥回调体：已直接覆盖；`HostKeyPolicy` 抽取仍可选

Task 4 收尾时把回调体（find → 比对 → 询问 → 落库）用五条用例直接钉住了，接线也由
两条直接断言守着（构造点 + `connect()` 自己的传参路径），所以**「这个安全控制没有
任何见证」这个洞已经堵上**：把 `onVerifyHostKey` 改成 `null` 现在会让 7 条用例变红，
而在修之前，同样的改动**整套用例全绿**。

评审建议的进一步抽取（把回调体提成独立的 `HostKeyPolicy`，`_buildHostKeyCallback`
退化成两行适配）**没有做**：现在没有哪条性质因为没抽取而失去约束。它的价值在可读性
与「让 `SshSession` 少两个 `@visibleForTesting` 成员」。**V1.1 候选**，不阻塞任何任务。

#### 4. `Session` 契约没有写「`connect()` 抛了之后仍需 `close()`」（文档缺口）

`session.dart` 的 `close()` 文档只说了「关闭会话」。但 `connect()` 中途失败
（例如 `client.shell()` 抛）会留下一个**还活着的**传输层与 socket，它们只被会话对象
引用着；这些资源之所以最终会被释放，**只是**因为 Task 6 的 `_teardownSession`
无条件调用 `session.close()`。

**这是一条隐性的依赖，不是设计。** 修法两选一：在 `Session.close()` 的文档里写明
这个义务，或者让 `connect()` 在自己的失败路径里就地清理。建议前者（改动最小，且对
Telnet 同样成立）。属于计划 3 或计划 5 的顺手项。

#### 已经如实披露、不打算在 Task 4 关闭的一条

`SshSession` 的输出流订阅（`.listen(..., onError: _onError, ...)`）**没有任何用例钉住
接线本身**：把 `onError: _onError` 整个从 `.listen` 上去掉，Task 4 的 24 条用例
**全绿**（实测）。用例覆盖的是 `_onError` 的**函数体**（经 `debugReportOutputError`
那个缝），不是「它被接上了」。关闭它需要一个能真正报错的 stdout 流，而那要先握手成功
—— 即 Task 7 的真 `sshd`，本 Task 明令禁止造假服务端。计划 Task 4 的「覆盖不到的
部分」一节已按实测如实写明，**别把「已披露」读成「已覆盖」**。

### 13.22 「转发的每个名词」都要有断言读它（计划 2 Task 5 执行期，2026-09-25）

`SessionFactory` 几乎只做两件事：按协议分发、把构造参数原样转发（全类 56 行，`create`
占 18 行）。它的测试**写了三轮才把转发钉住**，三轮的洞是同一形状、逐层更深，而且
**三轮都是由变异表抓出来的，没有一轮是读代码看出来的**。

1. **第一轮：显式传入的值没被约束。** 4 条用例只钉住「协议 → 类」和「每次新实例」。
   把 `verifyHostKey: false` 硬编进工厂的转发行，**全仓 188 条用例全绿**（实测）。
   这是 NFR-S-03 / FR-C-11 的整线静默绕过 —— 应用里每一台设备的会话都从这一行走。
   同轮还有一条更值得记的：名为「可以把建连方式换掉（计划 3 的跳板机靠这个注入）」的
   用例（**用例名里的「计划 3」已随跳板机放弃而失效（§10.2），但它守的注入点仍然
   是 SOCKS5 代理等 V1.1 候选的前提，所以用例本身不删**），注入的 resolver 返回的
   正是默认的 `const DirectConnector()`
   （`const` 会被规范化，两者 `identical`），于是**它断言的恰是自己名字的反面**。

2. **第二轮：没传时的默认值没被约束。** 补上转发断言后，把 SSH 分支的 `profile`
   换成另一个 `DeviceProfile`（id / host / username 全不同）→ **7 条全绿**。
   洞从「传进去的值」移到了「不传时的默认值」。

3. **第三轮：注入函数收到的入参没被约束。** 再补上默认值后，把交给
   `connectorResolver` 的 profile 换成另一个（会话仍拿到真 profile，故 6/7/8 不动）
   → **8 条全绿**。resolver 只有一个入参，而（原计划 3 的）跳板机正是靠它选链 ——
   跳板机虽已放弃，但注入点是「换一种建连方式」这件事的唯一入口，所以这条约束继续成立。

**判据（比上面三条更好记）：用例名字里出现的每一个名词，都必须有一条断言真的去读它。**
三轮的洞全是「名字声称覆盖、断言从不读它」的格子 —— 这也解释了为什么它们躲过了三轮
人工阅读，却一进变异表就现形。

**这条缝现在是闭合的，且有结构上的理由，不是「想不出新点子了」：** 把类的全部输入
（`profile` 与 5 个字段）交叉全部去向（会话 / resolver 入参 / 默认值）列出来，每一格
都有对应的变异行。剩下的三条绿变异**不是洞，别去补行** —— ①resolver 被调用**两次**
（第二次结果丢弃）：`Connector` 是惰性的（`open()` 才是唯一 IO 入口），按新增的
typedef 注释，构造路径本就不该有 IO，钉调用次数只会冻住实现细节；②连接器被缓存：
当前默认 resolver 返回规范化的 `const DirectConnector()`，**不同 profile 返回同一个对象
是合法的**，所以「不同 profile ⇒ 不同连接器」这条看似自然的断言是**错的**；
③`switch` 的主语不是 `profile.protocol`（实测把主语换成按端口猜协议，8 条全绿）：
夹具里 `protocol` 与 `protocol.defaultPort` 是耦合的，**「主语恰好是某个表达式」原则上
钉不住**，只能钉具体替代品。

**给 Task 6 的提醒：** `ConnectionManager` 的注入面比这里大得多（`SessionFactory`、
时钟/定时器），而它同样以「转发 + 编排」为主。**先按上面那条判据过一遍再写测试** ——
三轮返工比一次写对贵得多。

### 13.23 批跑变异时 `flutter test` 的两种终止行为（计划 2 前置，2026-09-25 实测）

一次批跑变异卡了 **13 分钟**，当时的结论是「`flutter test` 在加载/编译失败之后**不退出**，
会一直挂着」。**这个结论是错的**，两种形状都实测过，都会正常终止：

1. **编译失败**：`test/` 下放一个语法错误文件，`timeout 75 flutter test <该文件>` →
   **exit 1，耗时 1 秒**。红行点名的是**文件路径**
   （`loading …/zz_hang_probe_test.dart [E]`、`Compilation failed for testPath=…`），
   按既有判据这是**假红**，什么都不证明。
2. **永不完成的用例**（`await Completer<void>().future`，也就是"删掉超时守卫"会造出的
   形状）→ **exit 1，耗时 32 秒**，是**框架自己的 30 秒单测超时**兜掉的。红行点名
    **用例名**，所以它是真红，但成色是超时而非断言 —— 与 Task 4 第 23 条同一条教训：
   一条红的成色是夹具的属性。

**所以"卡住"不能用"工具链不退出"解释。** 那次事故的现场证据是：除主进程外还有
**两个孤儿 `flutter` 进程**需要一并杀掉 —— 这指向**重叠的 `flutter test` 调用在抢
构建锁**，而不是测试本身挂着。

**操作规则（Task 6—8 的批跑照此执行）：**

- 每行**仍然**加硬超时（`timeout`），这是便宜的保险，且上面第 2 条说明确实存在
  要等 30 秒的行；
- 批跑**不要并行** `flutter test`，一个进程跑完再起下一个；
- 某行**超过约 2 分钟**还没返回时，先 `pgrep -af flutter` 看有没有孤儿进程 / 锁竞争，
  **先杀掉孤儿再重跑那一行**，不要就此判定"这行变异有问题"或"工具链会挂"；
- 判红仍然只看**点名用例的 `[E]`**：点名文件路径的一律不算证据。
