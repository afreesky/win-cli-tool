## 1. 项目概述

### 1.1 一句话定义

一个 Flutter 桌面应用，同时保持与多台网络设备的长连接会话，让运维人员在同一个窗口里编辑命令、按行或按选区下发，并实时查看回显。

### 1.2 背景

网络运维的日常是在十几台到几十台设备之间反复切换、敲命令、看回显。常见的做法是开一堆 SecureCRT / PuTTY 窗口，问题在于：

- 窗口数量随设备数量线性增长，切错窗口是常事
- 同一条配置要在多台设备上重复敲，或者依赖自研脚本
- 命令是从文档、邮件、工单里复制来的，粘贴到终端里容易漏行、错行
- 事后想查"我到底敲了什么、设备回了什么"，终端的历史缓冲靠不住

本工具要解决的是前三点中的**编辑与下发**环节：把"要发哪些命令"变成一件可编辑、可选择、可视化的事，再交给程序按正确的节奏逐条下发。

### 1.3 设计目标

1. **多设备并驻**：多台设备的长连接同时保持，切换设备零等待
2. **下发可控**：命令以文本行的形式先落在编辑区，用户明确指定发送范围后才下发
3. **节奏正确**：网络设备 CLI 必须逐条下发、等回显完成再发下一条，否则命令会串行错乱
4. **输出可信**：输出是该设备会话的完整流，含设备回显，且默认落盘可追溯

### 1.4 非目标

本工具**不是**终端模拟器。它不做全屏 TUI 程序（如 `top`、`vi`）的交互渲染，不追求像素级还原设备终端画面。它的定位是「面向网络设备 CLI 的命令批量下发与回显查看工具」。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| **设备（Device）** | 一台被管理的远端设备，含连接参数与显示名称 |
| **会话（Session）** | 与某台设备建立的一条长连接。一台设备同时最多一条会话 |
| **设备列表** | 左侧面板中按钮形式的设备集合 |
| **当前设备** | 用户选中、编辑区与输出区正在跟随之的设备 |
| **编辑区** | 命令编辑窗口的文本区域 |
| **输出区** | 命令执行输出窗口的文本区域 |
| **命令队列** | 待下发的命令序列，按设备隔离，串行执行 |
| **提示符（Prompt）** | 设备 CLI 等待输入时显示在行尾的标记，如 `[CoreSW]`、`Router#`、`<Huawei>` |
| **静默去抖** | 命中提示符后额外等待一段无新数据的时间，用以排除误判 |
| **翻页提示** | 设备分页输出时的 `--More--` 类标记 |
| **命令库** | 用户维护的可复用命令片段集合，每台设备独立一份 |

## 3. 用户与典型场景

### 3.1 目标用户

负责网络设备日常运维与配置的网络工程师。熟悉设备 CLI，习惯逐条敲命令并观察回显，关心"命令有没有真的生效"。

### 3.2 典型场景

**场景 A：单设备配置下发**
运维人员接到工单，需要在核心交换机上给 8 个接口加描述。他把命令从工单里粘贴进编辑区，检查一遍，拖选这 8 行，点发送，然后盯着输出区逐条确认。中途发现第 5 条写错了，点"停止"，改掉再重发剩下的。

**场景 B：多设备巡检**
运维人员同时连着 6 台设备，逐个点设备按钮切换，在各自编辑区里保留着不同的巡检命令（切回来还在），挨个发送并查看结果。

**场景 C：事后追溯**
三天前某台设备上做过一次配置变更，需要确认当时执行了什么、设备回了什么。从日志目录里直接翻出那天那台设备的记录。

**场景 D：经堡垒机接入**
生产设备在隔离网段，只能经堡垒机跳转。运维人员在工具里配好一次堡垒机，之后新增设备时只需勾选它，不必每台设备重复填一遍堡垒机口令。20 台设备同时在线时，工具对堡垒机只维持一条 SSH 连接、按需开转发通道，不会撞上堡垒机的并发会话限制。

## 4. 功能需求

### 4.1 设备管理（FR-D）

| 编号 | 需求 |
|---|---|
| FR-D-01 | 用户可以添加设备。添加时需填写：**显示名称**（用户指定）、协议（SSH / Telnet）、主机地址、端口、用户名、密码 |
| FR-D-02 | 协议为 SSH 时，可选使用私钥文件认证替代密码认证 |
| FR-D-03 | 端口默认值：SSH 为 22，Telnet 为 23；用户可覆盖 |
| FR-D-04 | **显示名称在设备列表内必须唯一**。添加或编辑时若重名，给出明确提示并拒绝保存 |
| FR-D-05 | 用户可以编辑已有设备的任意字段 |
| FR-D-06 | 用户可以删除设备。删除前二次确认。删除时断开其连接，并一并删除其草稿与命令库；**日志文件保留** |
| FR-D-07 | 用户可以调整设备在列表中的顺序（拖拽排序） |
| FR-D-08 | 设备列表**用按钮形式**呈现，每个按钮显示设备名称与其连接状态 |
| FR-D-09 | 设备按钮上的状态指示：灰=未连接，黄=连接中或重连中，绿=已连接，红=连接失败或已断开 |
| FR-D-10 | 设备列表在应用重启后完整恢复 |
| FR-D-11 | 每台设备可配置「登录后执行」命令列表（多行文本），见 FR-C-08 |
| FR-D-12 | 每台设备可标记「启动时自动连接」，见 FR-C-14 |
| FR-D-13 | 每台设备可指定一条**有序的跳板机链**（0 个表示直连），见 FR-J-03 |

### 4.2 连接管理（FR-C）

| 编号 | 需求 |
|---|---|
| FR-C-01 | 应用**同时保持多台设备**的连接，互不干扰 |
| FR-C-02 | 采用**长连接常驻**模型：设备连接建立后持续保持，不因命令执行完毕而断开 |
| FR-C-03 | 点击设备按钮 = 将其设为当前设备。若该设备尚未连接，**同时发起连接** |
| FR-C-04 | 点击已连接的设备按钮仅做切换，不断开连接 |
| FR-C-05 | 用户可以在设备编辑对话框中主动断开某台设备的连接 |
| FR-C-06 | 连接失败时，设备按钮变红，并在输出区给出可读的失败原因（连接超时 / 认证失败 / 主机不可达 / 协议错误 / 跳板机失败，见 FR-J-05） |
| FR-C-07 | **断线自动重连**：检测到会话意外断开后，按指数退避自动重连：1s → 2s → 4s → 8s → 16s → 30s 封顶，此后维持 30s 间隔持续重试 |
| FR-C-08 | 连接成功后，自动依次下发该设备的「登录后执行」命令（如 Cisco 的 `enable`）。**每次重连成功都要重新执行** |
| FR-C-09 | 重连成功时，在输出区插入一条醒目的分隔标记，标明断线时段与重连时刻 |
| FR-C-10 | 断线时，**命令队列中尚未发出的命令一律丢弃，不自动重放**。输出区给出告警 |
| FR-C-11 | SSH 首次连接某主机时，弹出主机密钥指纹供用户确认，确认后保存。设置中可全局关闭该校验 |
| FR-C-12 | 关闭应用时，直接关闭所有会话，**不向设备发送任何命令**（避免意外改变设备状态） |
| FR-C-13 | 连接超时默认 15 秒，可在设置中调整 |
| FR-C-14 | 被标记为「启动时自动连接」的设备，在应用启动后自动发起连接 |

**FR-C-10 的理由**：网络设备上的命令多为配置下发。断线重连后自动重放队列，可能导致同一条配置被下发两次（例如 `interface X` / `shutdown` 这类命令重复执行后果不可逆）。宁可让用户重新确认。

### 4.2.1 跳板机（FR-J）

设备位于隔离网段、必须经堡垒机才能访问时，使用 SSH 跳板机（等价于 OpenSSH 的 `ProxyJump`）。

| 编号 | 需求 |
|---|---|
| FR-J-01 | 用户可以添加、编辑、删除跳板机。字段：名称、主机地址、端口、用户名、密码或私钥文件 |
| FR-J-02 | 跳板机列表**全局共享**，不随设备重复定义。这样堡垒机口令变更时只需改一处 |
| FR-J-03 | 每台设备可指定一条**有序的跳板机链**：0 个表示直连，1 个为常见单跳，N 个为多跳 |
| FR-J-04 | 连接时按链序逐跳建立 SSH 连接并逐跳认证 |
| FR-J-05 | 任一跳失败时，错误信息必须**指明是第几跳失败**（如「第 1 跳 堡垒机-A 认证失败」），便于定位 |
| FR-J-06 | 跳板机链中的每一跳都需遵守 FR-C-11 的主机密钥校验规则 |
| FR-J-07 | 同一跳板机链的**前缀连接在多个设备间复用**：N 台设备共用同一台跳板机时，只建立 1 条到跳板机的 SSH 连接，为每台设备各开一条转发通道。跳板机连接按引用计数释放，无设备引用时关闭 |

**FR-J-07 的理由**：堡垒机普遍限制单用户的并发会话数（常见 5～10）。若每台设备各建一条到堡垒机的连接，接 20 台设备会直接撞上限制，且失败原因难以诊断。dartssh2 的转发通道天然支持一条 SSH 连接上开多个 `direct-tcpip` 通道，因此复用的边际成本很低。

**FR-J-01/FR-J-02 的理由**：堡垒机是共享基础设施，若把凭据内联进每台设备，改一次堡垒机口令要编辑全部设备。

### 4.3 命令编辑与下发（FR-E）

| 编号 | 需求 |
|---|---|
| FR-E-01 | 编辑区支持输入任意行命令，支持多行文本 |
| FR-E-02 | 编辑区左侧显示行号 |
| FR-E-03 | 编辑区内容**按设备独立保存**。切换设备时编辑区整体切换；切回时内容仍在 |
| FR-E-04 | 编辑区草稿在应用退出时落盘，重启后恢复 |
| FR-E-05 | 用户可以用鼠标点击定位光标到任意行 |
| FR-E-06 | 点击「发送」按钮时的发送范围：**有选中文本时发送选中的所有行；无选中时发送光标所在的那一行** |
| FR-E-07 | 发送时按编辑区中自上而下的顺序下发 |
| FR-E-08 | **完全空白的行在发送时被跳过**（不产生空回车污染回显）。确需发送空行时，在行内输入一个空格 |
| FR-E-09 | 每条命令自动补行尾符。默认 `\n`，可按设备切换为 `\r\n` |
| FR-E-10 | 下发采用**串行**方式：发第 N 条 → 等待该条执行完成 → 再发第 N+1 条。同一设备同一时刻只有一条命令在途 |
| FR-E-11 | 「执行完成」的判定见 §5.2 |
| FR-E-12 | 命令执行超时（默认 10s）时，输出区插入醒目告警行，并**强制放行下一条**，避免整个队列卡死 |
| FR-E-13 | 用户可以**中止命令队列**：点击「停止」后，不再发送队列中剩余的命令；已发出的命令不做处理 |
| FR-E-14 | 编辑区中正在发送的行，以及队列进度（如「执行中 3/8」）需要可视化指示 |
| FR-E-15 | 支持从本地文件导入命令到编辑区。导入时询问「替换现有内容」或「追加到末尾」 |
| FR-E-16 | 导入仅支持 UTF-8 编码。遇到非 UTF-8 内容时给出明确提示，而非静默乱码 |
| FR-E-17 | 支持把当前编辑区内容同步给另一台设备：选择目标设备后，指定「覆盖」或「追加」到目标设备的草稿。用于同一条命令需要在多台设备上执行的场景 |

### 4.4 输出显示（FR-O）

| 编号 | 需求 |
|---|---|
| FR-O-01 | 输出区显示当前设备的会话输出流，**包含设备回显**（即能看到"我发了什么"和"设备回了什么"）。其观感接近真实终端 |

| FR-O-06 | 输出区文本可被鼠标选中并复制 |
| FR-O-07 | 输出缓冲区有上限（默认保留最近 5000 行），超出部分丢弃最旧的行。日志文件不受此限制 |

| FR-O-09 | 切换设备时，输出区整体切换为该设备的输出流；各设备的输出缓冲各自保留 |

## 5. 关键行为规则（详细定义）

本节是实现与验收的直接依据，规则的边界情况必须按此实现。

### 5.1 发送范围判定

```
if (编辑区存在非空选中范围) {
    取出选中范围内覆盖的所有行，按自上而下顺序
} else {
    取出光标所在的那一行（光标视为落在该行内）
}
过滤掉完全空白的行
若结果为空 → 不发送，给出轻提示
```

- 选中范围跨越部分行时，**该行只要被选中范围覆盖到任意一个字符，即整行参与发送**
- 选中范围的行序始终按编辑区自上而下，与用户拖拽方向无关

### 5.2 命令执行完成的判定

一条命令发出后，满足以下**全部**条件才判定其执行完成：

1. **提示符命中**：接收缓冲区中**最后一个非空行**（去掉行尾空白后）匹配提示符正则
2. **静默去抖**：自最后一个字节到达起，连续 **120ms**（可配）没有新数据到达

判定完成后立即释放队列，下发下一条。

**提示符正则默认值**：`[>#\]]\s*$`

覆盖华为 VRP（`<Huawei>` / `[Huawei]` / `[Huawei-GE0/0/1]`）、Cisco IOS（`Router>` / `Router#` / `Router(config)#`）、H3C 等主流形态。

**超时**：命令发出后 **10s**（可配）仍未满足上述条件，则：

- 在输出区插入醒目告警行，注明超时的命令序号与原命令文本
- **强制放行**下一条，队列继续

**为什么需要静默去抖**：设备回显中可能出现以 `>` 或 `]` 结尾的内容行。若只看正则命中最末尾，会在数据仍在流动时误判命令已结束。要求"数据停住 120ms"可以排除绝大多数误判。

### 5.3 翻页处理

- 检测接收缓冲区尾部是否存在翻页提示
- 默认匹配模式：`---- More ----`（华为/H3C）、`--More--`（Cisco）、`<--- More --->`，可在设置中扩充
- 命中后**立即回送一个空格**继续翻页
- 翻页动作**不计入命令队列**，也**不重置**提示符判定的静默计时器所属的命令
- 翻页不被视为"新命令"，因此不产生队列进度变化

### 5.4 断线与重连

| 事件 | 行为 |
|---|---|
| 检测到会话断开 | 设备按钮变黄（重连中）；输出区插入醒目标记；命令队列中未发出的命令全部丢弃并告警；启动指数退避重连 |
| 重连成功 | 设备按钮变绿；输出区插入分隔标记；自动重新执行「登录后执行」命令 |
| 重连失败 | 按退避序列继续重试，按钮维持黄色；连续失败在输出区给出提示，避免刷屏（同一原因只提示一次） |
| 用户主动断开 | 停止重连，按钮变灰 |

### 5.5 设备切换

切换设备时，以下内容**整体**随之切换：

- 编辑区内容（含光标位置与滚动位置）
- 输出区内容（含滚动位置）
- 命令库面板
- 输出区标题栏中的设备名

以下内容**不**随切换变化：

- 各设备的连接状态（后台保持）
- 各设备的命令队列（在后台继续执行，输出写入各自缓冲区）
- 日志写入（持续进行）

**注意**：在设备 A 的队列执行期间切到设备 B，A 的队列**继续执行**，输出写入 A 的缓冲区。切回 A 时能看到完整过程。

### 5.6 日志格式

```

[2026-09-24 14:30:12.340] [CoreSW]
[2026-09-24 14:30:18.902] [CoreSW]sys
[2026-09-24 14:30:18.910] Enter system view, return user view with Ctrl+Z.
[2026-09-24 14:30:18.915] [CoreSW]
[2026-09-24 14:31:02.114] !!! 连接断开 2026-09-24 14:31:02.114 ！！！

- 日志记录**剥离控制符后**的文本，与输出区所见一致
- 时间戳为本地时间

### 5.7 跳板机连接

建立一条经跳板机链 `[A, B]` 到目标设备的连接，实际过程为：

```
连接 A（SSH 直连）
  └─ 在 A 上开 direct-tcpip 通道，目标 = B:22        ← 得到一个双向字节流
       └─ 在该字节流上建立到 B 的 SSH 连接
            └─ 在 B 上开 direct-tcpip 通道，目标 = 设备:22
                 └─ 在该字节流上建立到设备的 SSH 连接（或运行 Telnet 协议）
```

| 规则 | 说明 |
|---|---|
| **逐跳认证** | 每一跳使用该跳板机自己配置的凭据 |
| **逐跳校验主机密钥** | 每一跳都遵循 FR-C-11，首次连接需确认该跳的指纹 |
| **通道而非端口** | 使用 `direct-tcpip` 通道，**不在本地绑定任何端口**。因此不会与其他程序争抢端口，也不引入本地监听的安全面 |
| **前缀复用** | 链 `[A]`、`[A, B]`、`[A, C]` 复用同一条到 A 的连接；到 B、C 的第二跳各自独立 |
| **引用计数释放** | 每台设备的会话对链上每个前缀各持有一个引用。设备会话关闭时递减，归零则关闭该跳板机连接 |
| **跳板机断线** | 跳板机连接断开会使**所有经由它的设备同时断线**，各自独立进入 FR-C-07 的重连流程。输出区需明确提示这是跳板机导致的批量断线，而非各设备各自故障 |
| **不在设备列表中展示** | 跳板机不作为设备出现，仅在连接链中隐式存在，其状态通过受影响设备的按钮状态间接体现 |

## 7. 界面设计

### 7.1 布局方案

**选定方案：左设备列表 + 右侧上下分割（编辑区在上、输出区在下）**

选择理由：

- **输出区必须拿到全宽**。网络设备的长配置行与 `display` 大表格在窄栏中会频繁折行，严重影响可读性
- 设备列表是纵向的，天然支持设备数量增长；顶部标签页方案在超过 5 台设备后开始拥挤
- 编辑区与输出区上下相邻，视线移动距离短，符合"改一行、发一条、看结果"的操作循环

## 8. 技术方案

### 8.1 技术选型

| 用途 | 选型 | 版本 | 说明 |
|---|---|---|---|
| 开发框架 | Flutter / Dart | 3.44.4 / 3.12.2 | 已在本机安装 |
| 状态管理 | `flutter_riverpod` | 3.4.3 | 按设备维度用 `family` provider 隔离会话、草稿、输出 |
| SSH | `dartssh2` | 4.1.0 | 纯 Dart，支持 PTY shell、密码与私钥认证，2026-09 仍在维护 |
| Telnet | **自研**（`dart:io` Socket） | — | 约 200 行：IAC 协商 + 控制序列剥离。理由见 §8.4 |
| 应用目录 | `path_provider` | 2.1.6 | 跨平台应用数据目录 |
| 命令行编辑器 | Flutter 原生 `TextField` | — | 不引入第三方编辑器包。行号栏独立渲染并与滚动同步；行级高亮通过覆写 `TextEditingController.buildTextSpan` 实现 |
| ANSI 颜色 | 自研极简 SGR 解析器 | — | 约 100 行：剥离 CSI/OSC 等非 SGR 控制序列，SGR 映射为 `TextSpan` 样式 |

**关于终端仿真**：明确不引入 xterm 类终端仿真器。理由是输出需要可搜索、可复制、可按行处理，且本工具的核心模型是"命令文本 → 下发 → 回显查看"，与终端仿真的画布模型不契合。网络设备 CLI 回显几乎全部是纯文本行，很少使用光标定位类控制序列。

### 8.2 架构分层

六层，自上而下单向依赖。核心服务层、传输层、连接建立层均不依赖 Flutter。

```
┌─ UI 层：Flutter Widgets ────────────────────────────────────┐

└─────────────────────────────────────────────────────────────┘
                            ↕
┌─ 状态层：Riverpod Providers ────────────────────────────────┐
│ devicesProvider │ settingsProvider │ sessionProvider(deviceId) │
│ draftProvider(deviceId) │ outputProvider(deviceId)             │
└─────────────────────────────────────────────────────────────┘
                            ↕
┌─ 核心服务层：纯 Dart ────────────────────────────────────────┐
│ ConnectionManager │ CommandDispatcher │ PromptDetector        │
│ MorePager │ AnsiParser │ LogWriter                            │
└─────────────────────────────────────────────────────────────┘
                            ↕
┌─ 传输层：Session 抽象接口 ──────────────────────────────────┐
│ Session（抽象） → SshSession（dartssh2） / TelnetSession（自研）│
└─────────────────────────────────────────────────────────────┘
                            ↕
┌─ 连接建立层：Connector 抽象接口 ────────────────────────────┐

                            ↕

|---|---|---|
| `ConnectionManager` | 所有会话的生命周期：建连、断开、断线检测、指数退避重连、状态广播；并持有每设备的 `CommandDispatcher` | `Session` 实现, `CommandDispatcher` |

### 8.4 风险与待验证项

**Telnet 层自研的决策依据**：原本的候选 `ctelnet` 0.3.1 有两个问题 —— ① 构造函数只接受 `host`/`port`，内部硬编码 `RawSocket.connect`，**没有 socket 注入点**，因此无法走跳板机；② 小包，2024 年后未更新。自研约 200 行可同时解决这两点，并去掉一个不受控的依赖。（顺带记录：pub.dev 上另一个主流包 `telnet` 锁定 `sdk: >=2.14.0 <3.0.0`，在本项目的 Dart 3.12 上**根本无法解析依赖**，从一开始就不在候选内。）

| 风险 | 影响 | 应对 |
|---|---|---|
| **自研 Telnet 层的兼容性** | Telnet 选项协商在真实设备上存在差异（回显模式、终端类型、窗口大小），自研实现可能有覆盖不到的组合 | ① 假设备服务器覆盖主流协商组合并做回归；② 协商异常时把完整收发字节记入日志便于定位；③ Telnet 设备多为内网环境，风险可控 |
| **跳板机连接池的生命周期** | 引用计数出错会导致两种相反故障：连接泄漏（占满堡垒机会话额度）或提前关闭（导致在用设备断线） | 连接池的增删收敛到单一模块，不散落在各处；用假跳板机做引用计数与「并发建连/断开」的单元测试 |
| **提示符正则的误判** | 设备回显中出现以 `>` / `]` 结尾的内容行会导致误判命令已结束 | 静默去抖（120ms）+ 只看缓冲区最后一个非空行 + 正则可按设备覆盖 |
| **Windows 产物构建** | Linux 开发机无法产出 Windows 桌面包 | 实现阶段落实 Windows 机器或 CI（GitHub Actions `windows-latest`） |
| **非 UTF-8 配置脚本** | 中文环境下存在 GBK 编码的配置文件，导入会乱码 | V1 仅支持 UTF-8 并给出明确提示；GBK 支持列入 V1.1 候选 |
| **明文凭据** | 配置文件泄露即凭据泄露 | 已接受该风险。存储接口独立封装，为后续替换预留（NFR-S-01） |
| **旧设备只提供已被淘汰的 SSH 算法** | `dartssh2` 4.x 已从默认算法集中移除 `ssh-rsa`/SHA-1、`diffie-hellman-group14-sha1`、`aes128-cbc`/`aes256-cbc`、`hmac-md5` 等。只提供这些算法的老设备**直接协商失败**，表现为「连不上」，而本工具的目标设备里这类机器占比不低 | **V1 明确不做兼容开关**（见 §10.1），失败时按 FR-C-06 给出可读原因。缓解：算法集在 `dartssh2` 里是 `SSHAlgorithms` 的一个参数，后续补充为纯增量改动，不需要动 `Connector`/`Session` 抽象 |

1. **真 `sshd` 回环集成测试（首选）**：在测试里用 `ssh-keygen` 现生成主机密钥与用户密钥，起一个监听 `127.0.0.1` 高位端口的 `sshd`，跑真实链路。已验证本机具备 `/usr/sbin/sshd` 与 `/usr/bin/ssh-keygen`（OpenSSH 8.0p1），且探测工程 `/tmp/wct-ssh-probe` 中 9/9 用例通过。**该测试必须带同步的可用性跳过守卫**（`sshd` 不存在、端口不可用、Windows 上无 `sshd` 时 `skip:` 而非失败），否则会在 CI 与 Windows 开发机上变成红灯。
2. **纯 Dart 单元测试（打底，始终运行）**：`JumpHostPool` 的引用计数与前缀复用、`Connection` ↔ `SSHSocket` 双向适配器、错误分类（FR-C-06 的五种原因）都做成不依赖真实 sshd 的纯逻辑测试，用假 `Connection`/假 `SSHSession` 驱动。

即：**能用真 sshd 的地方用真 sshd，不能用跳过，但打底的单元测试永远跑。**

## 10. 范围边界

### 10.1 V1 明确不做

| 不做项 | 说明 |
|---|---|
| 多设备群发 | 一次只对当前选中设备下发。设备按钮为单选 |
| 「命令 → 输出」分组关联 | 同一条命令可能重复执行，绑定语义上不成立。输出为统一流 |
| 输出区搜索/过滤 | 输出为统一流，V1 不做检索 |
| 完整终端仿真（xterm） | 见 §8.1 |
| 语法高亮 | V1 不引入 |
| SFTP / 文件传输 | 不在范围内 |
| 凭据加密存储 | 接口预留，实现留待后续（NFR-S-01） |
| 设备分组 / 文件夹 | V1 为平铺列表 |
| macOS 支持 | 不纳入 V1 交付范围 |
| 自动关闭设备分页 | 不做。不主动向设备发送厂商相关的初始化命令，改由用户通过「登录后执行」自行配置 |
| GBK 等非 UTF-8 编码导入 | V1 仅支持 UTF-8 |
| SOCKS5 / HTTP CONNECT 代理 | V1 只做 SSH 跳板机。`Connector` 抽象层已预留，后续补充实现为纯增量 |
| 跳板机的图形化管理之外的自动化 | 跳板机仅作为连接链的一环，不做跳板机自身的状态监控或会话管理 |
| 旧 SSH 算法的兼容开关 | `dartssh2` 4.x 默认算法集不含 `ssh-rsa`/SHA-1、`group14-sha1`、`aes*-cbc`、`hmac-md5`。**V1 不提供开启它们的设置项**：只提供这些算法的设备将协商失败（按 FR-C-06 报可读原因）。理由见 §10.2 |

### 10.2 已明确接受的风险

- V1 凭据以明文存储于 `devices.json`
- Telnet 协议本身明文传输（这是协议固有属性，非本工具的决策）
- **V1 只使用 `dartssh2` 的现代算法默认集，不提供旧算法兼容开关**（2026-09-24 决定）

  取舍：加上兼容开关意味着「每台设备多一个安全等级需要用户理解」，且开关一旦存在，用户遇到连接失败的第一反应会是「打开它」，从而在**本可以协商强加密**的设备和链路上也降级到 SHA-1/CBC。反过来，不加开关的代价是部分老设备在 V1 里连不上 —— 这个代价是**可见且可诊断**的（FR-C-06 会报协议错误），而不是静默的安全降级。

  三点缓解：① 该决策**不阻塞**任何架构 —— `SSHAlgorithms` 是 `dartssh2` 连接参数，后续补充只需改 `SshSession` 内部，`Connector`/`Session` 抽象不动；② 失败设备会走 FR-C-06 的可读原因路径，用户能立刻分清「连不上是因为算法」而不是逐个排查网络；③ 已列入 §12 的 V1.1 候选。

## 13. 实现阶段约束（执行期补充）

本节记录计划 1 执行期间由代码评审发现的、**不属于任何单个任务、但后续计划必须遵守**的约束。它不改变前 12 章的任何需求，只是把「已经踩过或即将踩到的坑」写下来，供编写计划 2–6 时对照。

**13.1 凭据读写必须走独立接口，不能在 store 里直接序列化模型（落实 NFR-S-01）**

`DeviceProfile.toJson()` 自身就会吐出 `password` 与 `privateKeyPath`。计划 4 若在 `DeviceStore` 里直接 `jsonEncode(profile.toJson())`，就把凭据存储焊死在了模型上 —— 而这正是 NFR-S-01 要求避免的：日后换系统密钥库将变成一次模型改动，而不是一次存储实现替换。正确做法是在 **Map 层** 处理：写入前剥离/替换 `password`，读取后在 `fromJson` 之前从凭据接口注入。模型本身保持冻结。

**13.2 设备顺序是隐式的**

§8.6 的 `devices.json` 没有 order 字段，数组顺序**就是**显示顺序。计划 4 必须保序（读写都不得重排）；计划 5 的拖拽排序（FR-D-07）要靠重写数组实现，**不能靠排序**。

**13.3 损坏的配置文件按条目隔离恢复**

§9.1 要求「损坏文件的恢复路径」。模型的 `fromJson` 用的是严格转型（`as int` / `as String`），手改坏一个字段抛的是 `TypeError` 而不是 `FormatException`。计划 4 必须**逐条目** try/catch：一台设备的坏记录不能让整个二十台设备的文件读不出来，且应上报是哪一条坏了。

**13.4 跳板机引用是跨对象不变量**

`DeviceProfile.jumpHostIds` 按 id 指向 `jumpHosts`。FR-J-02/03「被引用的跳板机不可删除」没有任何模型能承载，必须在计划 4 的 store 层校验。悬空 id 应当**在加载时上报**，而不是拖到连接时才失败。

**13.5 SSH 主机密钥指纹需要持久化，但模型里没有对应字段**

FR-C-11 / FR-J-06 要求首次连接确认后**保存**指纹。计划 2 早于计划 4，因此计划 2 必须接受一个**注入的**指纹存储或回调，而不是自己写文件 —— 否则持久化边界会漏成两处。

**13.6 列表字段目前是可变的共享引用**

`fromJson` 里 `jumpHostIds` 等用 `.cast<String>()`，返回的是惰性校验视图，且与调用方共享底层 list；`copyWith` 把同一个实例原样传下去。计划 5 的状态层若依赖 `==` 做变更检测会踩到。计划 4/5 视需要收紧为 `List.unmodifiable`。

**13.7 模型没有 `==` / `hashCode`**

目前一律按引用比较，这也是目前往返测试要逐字段写十几行 `expect` 的原因。计划 5 的 Riverpod 状态 diff、列表去重可能会需要值相等；若要补，优先补字段最少、最可能被 keyed 的 `Snippet`。

**13.8 `copyWith` 对「null 是有语义的值」的字段必须用哨兵**

这条约束适用于**任何**后续新增的模型类（计划 2 的 `KnownHost`、计划 4 的草稿模型等），不只是已经改好的那四个字段。

若某个可空字段的 `null` 表示一个**有定义的语义**（而不是「没有这个值」），它的 `copyWith` 参数就**不能**写成 `String? x` + `x ?? this.x` —— 那样「调用方没传」与「调用方显式传 null」不可区分，用户「清空」的操作会被静默变成「保持原值」，且返回一个完全合法的对象、不报任何错。

正确写法是哨兵，给出三种状态（不传→保留、显式 `null`→清空、传值→覆盖）：

```dart
const Object _unset = Object();   // 每个库一份，私有名不会跨库冲突

Foo copyWith({Object? bar = _unset}) => Foo(
      bar: identical(bar, _unset) ? this.bar : bar as String?,
    );
```

已按此改的字段：`DeviceProfile.password` / `.privateKeyPath` / `.promptRegex`、`JumpHost.password` / `.privateKeyPath`、`AppSettings.logDir`。

注意 `Object?` 参数会让**静态类型检查在这几个参数上失效**（传错类型能通过编译，运行时才抛 `TypeError`）—— 这是该惯用法的既定代价，换来的是三态语义正确。代价是「失败得更晚但仍然响亮」，不是「静默失败」。

判据是：**这个字段的 null 有没有语义**。列表字段（`jumpHostIds` 等）不该用哨兵，因为它们的「清空」是 `[]`，是个值不是 null。

**13.9 翻页提示会匹配提示符正则，判定「命令完成」时必须显式排除**

§5.2 的默认提示符正则是 `[>#\]]\s*$`，§5.3 的第三个默认翻页模式 `<--- More --->` **以 `>` 结尾**，因此它同时满足两者：

```
翻页尾巴=true  提示符匹配=true    <--- More --->
翻页尾巴=true  提示符匹配=false   ---- More ----
翻页尾巴=true  提示符匹配=false   --More--
```

后果不是「多翻一页」而是**命令静默丢失**：翻页分支回送空格后，静默去抖到点，`<--- More --->` 被当成提示符，命令被判为完成，下一条命令随即写进一个仍在等待翻页按键的设备 —— 该设备把这些字节当作翻页键吃掉，命令从未执行。用户看到「已发送、已完成」，配置却没生效（典型：`display current-configuration` 之后跟 `save`）。只要设备出下一页的耗时超过去抖阈值（120ms），在负载高或链路慢时就必然触发。

**约束：任何判定「命令结束」的地方，都要先排除翻页尾巴，再看提示符正则。** 这条不只约束计划 1 的 `CommandDispatcher`，也约束计划 2 的 `SshSession`（若它也做提示符判定）与计划 5 中任何重新推导命令状态的显示逻辑。

不要靠**修改翻页模式或提示符正则**来回避 —— 把 `<--- More --->` 改掉会破坏 H3C 设备识别。正确的修法是在「判定完成」这一步做排除。（对应 §8.4 风险表中「提示符误判」一项的具体形态。）

**13.10 未决缺口：翻页状态在超时或批次结束后会丢失**

承接 13.9。当前实现里，超时强制放行（§5.2）与批次正常结束都会清空接收缓冲区，于是「设备还停在翻页提示上」这一状态**没有任何地方记录**。若此时超时放行或用户发起下一批命令，新命令同样会被仍在翻页的设备吃掉，与 13.9 是同一个后果，但触发路径不同：13.9 已修，这一条**未修**。

规格本身也没给出答案 —— §5.2 只要求「超时后强制放行」，§5.3 只描述翻页中如何回送空格，两者都没说「强制放行时设备仍停在翻页上该怎么办」。可行方向有三，需要**明确选定一个**再写进 §5.3：

1. 缓冲区不清空，下一条命令发出前若尾部仍是翻页提示，先回送退出键（各厂商不一致：`q` / `Ctrl-C` / 空格翻到底）；
2. 不自动处理，改为向界面抛出「设备停在翻页」事件，由用户决定（更保守，不猜厂商行为）；
3. 超时时不回送、只告警，并在给出提示前持续回送空格把剩余分页翻完。

倾向 2：厂商退出键行为尚未在真机上验证（§8.4 已列为待验证项），在没验证前让程序猜按键，风险高于让用户看见。

**使这条缺口可达的是 10s 这个默认值本身。** 一条分页输出超过 10s 的命令（设备慢、链路延迟高，`display current-configuration` 这类大输出很容易超过）必然走到「超时放行时设备仍在翻页」，然后下一条命令被吃掉。因此定方案时还应一并考虑：**命令超时是否应当在翻页期间也照常计时**（当前实现照常计时，这是 §5.3 的要求）。缺口本身能自愈 —— 设备翻完后回到真实提示符，只损失一条命令 —— 但由它造成的「用户以为执行了、实际没执行」正是最需要避免的后果。

**13.11 `close()` 不得 await 单订阅 `StreamController` 的 `close()`**

`Session` 的实现内部用单订阅 `StreamController` 把「原始字节 → 解码后的文本」接起来。**单订阅 controller 的 `close()` 返回的 Future，要等到有监听者订阅、把 done 事件取走才会完成。** 没有监听者时它永远不完成：

```
未连接会话的 close()          → 永久挂起
无监听者的 controller.close() → 永久挂起
有监听者的 controller.close() → 正常完成
```

`TelnetSession` 里 `_decodeSub` 是在 `connector.open(...)` **成功之后**才挂上去的，因此有两类会话永远没有监听者：**从未连接过的**，以及 **connect 抛过异常的**（端口写错、拒绝连接、超时）。这两类会话上调 `await close()` 会永久挂起 —— 而「连不上之后清理」「切换设备」「关窗口」走的正是这条路。FR-C-12 要求退出时关闭所有会话，挂在这里就是应用退不掉。

**约束：`close()` 里只 await 真正的资源（订阅、socket），内存 controller 的 `close()` 用 `unawaited`。** 已连接的会话 `close()` 本来正常，别为此改成 broadcast —— 那会改变 `Session.output` 的语义（多个监听者、错过早期输出）。

计划 2 的 `SshSession` 会照搬这个结构，必须一并遵守。

**13.12 对端断开时 `TelnetSession` 不释放任何资源，且丢掉了异常对象**

`sessions`（会话实现）在收到对端的 `onDone` / `onError` 时只做一件事：完成 `done` 这个 Future。socket 不关、两个订阅不取消、`_dataBytes` 与 `_output` 不关闭、`_closed` 保持 `false`。也就是说 `done` 完成之后，这个会话**仍然接受 `write()` 并静默丢弃**，并一直持有资源，直到有人调用 `close()`。

计划 1 里不成问题 —— 每个调用方都记得关（e2e 的 `_Wired.dispose`、各测试的 `tearDown`）。但**计划 2 的重连正是最容易忘记的地方**：重连会新建一个会话，旧会话的 `close()` 一旦漏掉就是一个静默泄漏。约束：**`done` 完成不等于资源已释放，`close()` 仍必须调用**；计划 2 若改为在断开时自动释放，需同时确认不影响 `close()` 的幂等性。

另一半：`onError` 的错误对象被直接丢弃，于是「连接被重置」与「主机不可达」在调用方看来完全一样。FR-C-06 要求给出可读的失败原因，计划 2 需要把错误保留下来（新增错误事件或 `lastError`），而不是在这里丢掉。

**13.13 翻页状态应当用状态标志，而不是回头嗅探缓冲区**

13.9 的修复是在 `_checkPrompt` 里排除翻页尾巴，代价是「设备是否在翻页」这一状态**每次都由缓冲区内容重新推导**。这带来两个已知的次要问题：

1. 若设备把提示符**原地覆盖**在翻页提示上（同一行、中间没有换行），`stripAnsi` 去掉 `\r` 后两者会挤进同一行，`matchesTail` 持续为真，该命令就只能等 10s 超时放行 —— 多一个多余空格，外加每条分页命令白等一次超时。此形态未在真机验证，但代价不对称，值得记下。
2. 13.9 提到的 `MorePager` 用 `contains` 匹配，因此正常输出里只要出现 `--More--` 字样就会回送一个空格（B6）。收紧成 `endsWith` 会漏掉 `---- More ---- (24%)` 这类带后缀的提示，所以**不该那么改**。

两者同一个根因：**把「我们刚回过翻页键、还在等下一页」这件事记成一个显式状态标志，在新数据到达时清除**，比每次从缓冲区重新推断更可靠，也能一并消除上面两条。（计划 2 的 `SshSession` 若也做翻页判定，应直接采用状态标志的写法。）

**13.14 `dartssh2` 4.1.0 的行为与默认值（调研结论，计划 2 必须照此写）**

版本 4.1.0 已确认可在本项目的 Dart 3.12 上解析（8 个传递依赖，无冲突），与 §8.1 的选型一致。以下每一条都会让「照着直觉写」的代码出错：

1. **没有 `connect()`，且「信任校验」默认是关的 —— 但别和「签名校验」混为一谈。**
   API 是 socket 优先：自己建好 `SSHSocket`，交给 `SSHClient(socket, username: ...)`，再 `await client.authenticated`。

   这里有两个**不同**的开关，混淆它们会写出看起来安全、实际不安全的代码：

   | 构造函数参数 | 默认值 | 管什么 | 默认是否生效 |
   |---|---|---|---|
   | `disableHostkeyVerification` | `false` | **签名校验**：证明对端确实持有它出示的那把私钥 | ✅ 默认开启 |
   | `onVerifyHostKey` | `null` | **信任校验**：这把密钥是不是我们**期望**的那把（TOFU/已知主机） | ❌ **默认形同关闭** |

   源码 `ssh_transport.dart:1919` 写得很直白：

   ```dart
   final userVerified = onVerifyHostKey != null
       ? await Future.value(onVerifyHostKey!(_hostkeyType!.name, fingerprint))
       : true;        // 回调为 null ⇒ 直接当成"已验证" ⇒ 接受任意主机密钥
   ```

   也就是说：默认配置下握手本身的密码学是健全的，但**对端是谁完全没有被检查** —— 任何持有有效密钥的中间人都能冒充目标设备。这正是 NFR-S-03 要求默认开启的那一项，而「什么都不传」等于静默关掉了它。

   **约束：`SshSession` 必须始终显式传 `onVerifyHostKey`。** 即便全局设置关闭了校验（FR-C-11 允许），也应传一个显式 `(t, f) => true` 的回调，而不是留 `null` —— 让「校验被关掉」这件事在代码里**可见、可 grep、可评审**，而不是藏在构造函数默认值里。

   `fingerprint` 参数已经是可直接显示给用户的 UTF-8 字节（形如 `SHA256:<base64>`），`utf8.decode` 之后即可展示，不需要自己再算哈希。

2. **主机密钥被拒绝，抛出的是 `SSHAuthAbortError` 且 `.reason` 为 `SSHHostkeyError`。**
   FR-C-06 要求区分「认证失败」与「协议错误」，因此**不能把这个异常和密码错误一起归为「认证失败」** —— 用户看到「认证失败」会去改密码，而真正要改的是接受指纹。

3. **`SSHSession.flush()` 不可用。**
   调用它会丢出一个未处理的异步错误，且写入内容丢失。因此 `SshSession` 对 `Session.flush()` 的实现必须是**空操作**，不能转发给 dartssh2。（`Session` 接口里保留 `flush()` 是为了 Telnet 侧，SSH 侧不适用。）

4. **`SSHSession.stdout` 是 `Stream<Uint8List>`，照抄 Telnet 的管道会在运行时报错。**
   与 §8.5 `connector.dart` 中 `_SocketConnection.input` 记录的**同一个协变陷阱**：静态类型兼容，但 `Stream.transform` 按运行时类型校验 transformer，于是 `.transform(Utf8Decoder())` 编译通过、运行时抛 `type 'Utf8Decoder' is not a subtype of type 'StreamTransformer<Uint8List, String>'`。**必须 `.cast<List<int>>()`。** Telnet 侧已经踩过并写下了注释，SSH 侧是同一条坑。

5. **`session.close()` 不完成 `session.done`，但 `client.close()` 会 —— 而 `SshSession.close()` 两个都要调。**
   实测（2026-09-24，回环 sshd，见下表）四种路径：

   | 触发方式 | `session.done` | 是否符合 `Session.done` 契约 |
   |---|---|---|
   | 我方 `session.close()` | 保持未完成 | ✅ 符合 |
   | **我方 `client.close()`（会话仍活着）** | **完成** | ❌ **违反** |
   | 对端 `exit` | 完成 | ✅ 符合（就是要的信号） |
   | 底层 socket 被销毁 | 完成 | ✅ 符合 |

   第二行是陷阱：`SshSession.close()` **必然**会调 `client.close()`，于是「主动关闭」会被 `done` 的监听者看成一次**意外断线**。后果不是少一个信号，而是**退出应用或用户主动断开时，每台设备都触发一次 FR-C-07 自动重连** —— 用户点了断开/关了窗口，工具却在拼命重连。

   **约束：`SshSession` 转发 `session.done` 时必须先查 `_closed` 标志（`if (_closed) return;`），不能直接透传。** 这与 `TelnetSession._onDisconnected` 里的写法一致。已实测该守卫**充分且必要**：带守卫时主动关闭 0 个事件、对端断开 1 个事件；去掉守卫则主动关闭也报 1 个事件。因此这一条可以直接写成一对互为反向的回归测试（主动关闭 → `done` 不完成；对端断开 → `done` 完成）。

6. **`keepAliveInterval` 默认 10 秒。**
   对 FR-C-07 的重连有直接影响：设备侧静默断开时，dartssh2 会先靠自己发现的 keepalive 失败来结束 `done`，而不是等 TCP 超时。计划 2 若要调整该值，需与 FR-C-07 的退避序列一起考虑，避免「keepalive 判定断开」与「重连退避」互相打架。

7. **`SSHForwardChannel.close()` 会挂起，必须用 `destroy()`。**（计划 3 的跳板机直接受影响，先记在此处。）
   通道关闭是 `close()` 还是 `destroy()` 属于**必须显式选对**的一类 API —— 选错的表现是关连接时永久挂起，与 13.11 的症状相同但根因不同。

**13.15 FR-C-06 的错误分类必须看 `SSHAuthAbortError.reason`，不能看顶层类型或消息**

实测（2026-09-24，回环 sshd）三种失败的异常形态：

| 场景 | 抛出的异常 | `.reason` |
|---|---|---|
| 主机密钥被用户拒绝 | `SSHAuthAbortError(Connection closed before authentication)` | `SSHHostkeyError(Hostkey verification failed)` |
| **设备只提供旧算法**（`ssh-rsa`/`group14-sha1`/`aes128-cbc`/`hmac-md5`） | `SSHAuthAbortError(Connection closed before authentication)` | `SSHInternalError(Bad state: No matching key exchange algorithm)` |
| 认证失败（口令/密钥不对） | `SSHAuthFailError` | 无 `reason` 字段 |

**前两行的类型与 `toString` 完全相同。** 因此：

- 若分类逻辑看**顶层类型**或**消息文本**，则「主机密钥被拒」与「设备太旧、算法协商不了」会被归成同一类，而 §10.2 已决定 V1 不支持旧算法 —— 也就是说**用户会看到「认证失败」**，然后去反复检查一个根本没问题的口令。这正是 FR-C-06 要避免的「不可读的失败原因」。
- **唯一可靠的判据是 `.reason`**：`SSHHostkeyError` → 主机密钥问题（要提示用户去确认指纹，不是去改口令）；`SSHInternalError` → 内部/协商错误，归入「协议错误」。
- `SSHInternalError` 里的算法协商失败**只能靠消息文本**（`'No matching key exchange algorithm'`）识别。这很脆弱，因此分类器对**认不出的 `reason` 必须优雅降级**：归入「协议错误」并**附上原始消息**，而不是抛出去或吞掉。

另外要注意 `dartssh2/src/ssh_errors.dart` 里 `ssh_transport.dart:1408/1482` 抛的是**裸 `StateError`**，但它**不会**逃到调用方 —— 已被包装进 `SSHInternalError` 再放进 `reason`。所以分类器的 `catch` 仍应以 `SSHError` 为主，同时保留一个兜底分支处理非 `SSHError` 的意外异常。

对应用例（计划 2 必须覆盖）：三个场景各自的分类结果，其中**第一行与第二行必须分类不同** —— 这是这条约束的回归测试。

**13.16 测试可控性：三条实测事实（计划 2 预演中得到，含一个被否定的猜测）**

计划 2 的代码在写入计划前先抽出来编译并跑过一遍，过程中撞到下面三条。它们不是风格偏好，是**会把测试写成假测试或假失败**的坑。

1. **`fake_async` 推不动完整的「拆除」链 —— 用 `await` 串起来的 `cancel()` / `close()` 不会在 fake zone 下完成。**

   实测形态：`ConnectionManager.dispose()` → `_teardownSession()` → `await _dispatcher?.dispose()`，在 `fakeAsync` 里停在最后一步不再往下走，`session.close()` 因此**根本没被执行**，测试断言 `closed == true` 假失败。同一段代码换成真实 async，`closed` 立即为 `true`。

   关键旁证：卡住时 `async.pendingTimers.length == 0` 且 `async.microtaskCount == 0` —— **没有任何待推进的工作**，所以 `flushMicrotasks()`、`flushTimers()`、`elapse()` 都无效。这不是"少 flush 一次"的问题。

   **约束：涉及拆除（cancel / close / dispose）的断言一律用真实 `async` 测。** 拆除本身不涉及计时，真实 async 更直接也更强。`fakeAsync` 只留给**需要控制时间**的用例（退避序列、超时、断线时长）。

2. **广播 `StreamController` 的 `close()` future 并**不**等待订阅者取消 —— 这一条是为了否定一个看似合理的猜测。**

   我一度推断"`await dispatcher.dispose()` 会挂住，是因为广播 controller 的 `close()` 要等所有订阅者取消"，并据此设计了修复（先取消自己的订阅）。**实测否定了这个推断**：`StreamController.broadcast()` 在「有活跃订阅者」「无订阅者」「订阅者已取消」「单订阅 controller」四种情形下，`close()` 的 future 都**立即完成**（`package:fake_async` 内外都一样）。

   所以第 1 条的成因**尚未定位**（已排除：订阅者数量、订阅者取消、zone 一致性、嵌套 async 层数、dispatcher 单独调用）。**不要在没重新实测的情况下把它归因到 broadcast 语义上。**

   但由此得到的**设计结论仍然成立**：`session.close()` 不该挂在 `dispatcher.dispose()` 的 future 后面 —— 订阅 `dispatcher.events` 的不止 `ConnectionManager`（界面也会直接订阅），让 FR-C-12 依赖一个我们控制不了的 future 是错的。`dispose()` 的**同步**部分（`_disposed = true`、清空队列）立即生效，fire-and-forget 足以保证"不再发出任何命令"。

3. **`Uint8List` 的 `runtimeType` 与类型字面量 `Uint8List` 不 `==`。**

   `expect(value.runtimeType, Uint8List)` 会失败，且失败信息是 `Expected: Uint8List, Actual: Uint8List` —— 极具误导性（实测：`seen == Uint8List` 为 `false`，`identical(seen, Uint8List)` 也为 `false`，而 `value.runtimeType.toString()` 打印出来就是 `Uint8List`）。

   **约束：断言类型一律用 `expect(value, isA<T>())`，永不用 `expect(value.runtimeType, T)`。**

4. **时间源必须用 `clock.now()`（`package:clock`），不能用 `DateTime.now()`。**

   `fake_async` 推进的是 `clock`；`DateTime.now()` 走真实时间。用后者的话，测试里 `elapse(1s)` 之后算出来的时长恒为 0 秒，FR-C-09 的「断线时长」永远断言不了（实测：`fakeAsync` 里 `elapse(7s)` 后 `clock.now()` 恰好前进 7s）。

   `clock` 通常已在传递依赖里，但**必须**在 `pubspec.yaml` 里显式声明为直接依赖才能 `import`。

### 13.17 `ConnectionManager` 的三处实测结论（计划 2 执行期）

1. **用户主动断开时，状态必须是 `disconnected`（灰），不是 `failed`（红）—— 而 `_userClosed` 必须同时守住失败分支。**

   §5.4 的表格写的是「用户主动断开 → 停止重连，按钮变灰」。但只把 `disconnect()` 里的状态设对是不够的：用户在 `session.connect()` **还没返回**时点"断开"，`disconnect()` 会关掉 socket，于是那个在途的 connect **抛错**并走进 `_attemptConnect` 的 catch 分支。

   若 catch 只判断 `_disposed`（而成功分支判断的是 `_disposed || _userClosed` —— 这个不对称就是漏洞本身），后果有两层：
   - 发出一条**假告警**：这次失败是我们自己关 socket 造成的，设备没有任何问题；
   - 经 `_scheduleRetry()` 把状态刷成 `failed`，按钮**从灰变红**。

   实测证据（修复前）：`Expected: DeviceConnectionState.disconnected, Actual: DeviceConnectionState.failed`。

   **约束：`_attemptConnect` 的 catch 与 `_scheduleRetry` 都要在 `_userClosed` 时早退；`failed` 只留给 `!autoReconnect` 这一种情形，两者不可合并判断。**

2. **`CommandDispatcher.events` 是异步广播流，因此「转发订阅」是死代码 —— 一个看似成立的重复发送推断被证伪。**

   代码评审曾判断 `ConnectionManager` 里那个 `_dispatcherSub` 转发订阅（收到 `QueueDropped` 就 `_events.add(SessionLost(null))`）会导致**一次断线发出两个 `SessionLost`**：一个来自 `_onSessionDone`，一个来自转发。**实测不成立** —— 把那段代码原样放回去，断言 `lost.length == 1` 的测试**仍然全绿**。

   原因：`CommandDispatcher._events` 是 `StreamController.broadcast()`（**没有** `sync: true`，见 `command_dispatcher.dart:100`），`onDisconnected()` 投递的 `QueueDropped` 要等一个 microtask 才送达；而 `_onSessionDone` 在下一行就调用 `_teardownSession()`，后者在**同一个同步块**内取消 `_dispatcherSub`。转发监听器永远等不到那条事件。

   所以那段转发**从未触发过**，是死代码，而不是重复发送。删除它的理由因此是"它达不到注释宣称的效果"，不是"它会重复发送"。

   **同时要记住这条结论是顺序敏感的**：把 `_teardownSession()` 里那行 `cancel()` 挪到 `await outputSub?.cancel()` **之后**，转发就会收到事件、测试立刻变红（`expected 1, actual 2`）。所以约束的正确形态是**"不要订阅 `dispatcher.events` 去转发"**，而不是"记得及时取消订阅" —— 后者把正确性押在两行代码的先后顺序上。

   **约束：丢弃数（FR-C-10 的告警）由 `QueueDropped` 承载，界面直接订阅 `dispatcher.events` 取用（见 §13.16 第 2 条的设计结论），`ConnectionManager` 不转发命令队列的任何事件。** 另：**不要**再依据"广播流的 close/取消顺序"推断同类问题 —— 先测。这一节的第 2 条与 §13.16 的第 2 条是同一类教训。

3. **`failed`（红）在产品里何时可达 —— 一个尚未决策的 spec 冲突。**

   FR-C-06 要求「连接失败时，设备按钮变红」，但 `ConnectionManager` 的 `autoReconnect` 默认 `true`，且没有任何生产代码传 `false`（只有测试传过），于是 `failed` 在实际产品里**永远到不了**。这是 FR-D-09 与 §5.4 两处口径不一致的外显：

   - FR-D-09 概述为「红=连接失败**或已断开**」；
   - §5.4 的逐事件表却是：检测到断开→**黄**、重连失败→**维持黄**、用户主动断开→**灰** —— 表里**没有红**，也没为「首次建连就失败」留一行。

   两种读法（计划 2 暂按第 1 种实现，因为它与更具体的 §5.4 逐事件表一致）：

   1. 首次建连失败也走退避重连（黄），`failed` 仅留给 `autoReconnect == false`；则需修改 FR-C-06 的措辞，或明确「V1 暂不点亮红」。
   2. 首次建连失败立即变红（照 FR-C-06 字面），随后若要自动重连再转黄；则 `_attempt == 0` 的失败分支应置 `failed`，相关测试的首次断言也要改。

   另：`autoReconnect` 开关本身在 spec 里**没有依据** —— FR-G-01 的设置项列表里没有「自动重连」，而 FR-C-07 又要求断线后必须自动重试。若选第 1 种读法，需要新增一个设置项来承载它（属于计划 5），否则该参数应删除。

   **计划 2 的 Task 6 实现之前必须定下来。** 计划文件里同一项记在「未决项」一节。

### 13.18 `ConnectionSocket` 的三处实测结论（计划 2 Task 1 执行期）

1. **`sink` 必须是同步 controller，否则"写出去后立刻关闭"的字节会被静默丢弃 —— SSH 的优雅关闭报文就是这样丢的。**

   `SSHSocket.sink` 在本项目里由适配器自己用一个 `StreamController` 承接。**默认（异步）controller 会让 `sink.add` 推迟一个 microtask 才调用 `Connection.write`，而 `Connection.close()` 的关闭标记是同步置上的** —— 于是同一个同步块里"先写、后关"的字节，落到 `_SocketConnection.write` 时连接已标记关闭，被直接丢掉，不报任何错。

   实测（真 sshd + 真 `SSHClient`，通过一个记录调用顺序的 `Connection` 包装层观察）：

   | 场景 | 对端实际收到的字节 |
   |---|---|
   | 裸 `dart:io` Socket：`add([1,2,3])` 后同步 `close()` | `[1, 2, 3]` |
   | 适配器（异步 sink）：同上一个同步块 | **`[]`** |
   | 适配器：`add` 后让出一个 microtask 再 `close()` | `[1, 2, 3]` |

   在 `Connection` 上看到的调用顺序是 `[close, write-DROPPED(36B), write-DROPPED(36B)]` ——
   即 `SSHClient.close()` → `_closeChannels()` → `SSHChannelController.destroy()` →
   `_sendEOFIfNeeded()` / `_sendCloseIfNeeded()` → `socket.sink.add(...)`，全是同步调用，
   紧接在 `await _transport.close()` → `socket.close()` 之前。**`CHANNEL_EOF` 与
   `CHANNEL_CLOSE` 因此从未上线**，而裸 socket 路径下它们是发出去的 —— 也就是说这层
   适配器把一个原本正确的行为改坏了。

   代价不是抽象的：设备侧看到的是连接被粗暴掐断而非优雅断开。网络设备上这会占住
   vty 直到超时（Cisco/Huawei 都要 `clear line vty` 去清），对一个网络工程师工具是
   真实的操作负担。

   **修法**：`StreamController<List<int>>(sync: true)`。加 `sync: true` 后重测：
   `[write(36B), write(36B), close]`，两个报文都发出去了。

   **副带影响**：`Connection.write` 若同步抛错，现在会从 `sink.add` 里同步抛出，而不是
   变成异步未捕获错误。刻意如此（快速失败好过静默）。前提是监听回调不会回头再往
   同一个 sink 里写 —— 那会让 sync controller 抛 `StateError`。`Connection.write`
   不碰 sink，前提成立。

   **`_sink` 上那条 `onError` 是不可达的**：`Connection.write` 是同步 `void`，没有错误
   通道；而 `onData` 里抛出的异常**不会**路由到同一个订阅的 `onError`（实测：它会变成
   未捕获的 zone 错误）。留着它只为满足 `StreamSink` 的契约形态，别指望它兜住写入失败。

2. **`dispose()` 不关闭底层 `Connection`，且刻意返回 `void`。**

   `Connection` 是从调用方借来的，生命周期归调用方（计划 2 的 `SshSession.close()` 是
   先 `client.close()` 再 `dispose()`）。`dispose()` 只释放适配器自己的两个订阅。

   返回 `void` 而非 `Future<void>` 是**刻意的**：`dispose()` 里对两个 controller 的
   `close()` 只能 `unawaited` —— 单订阅 controller 的 `close()` Future 要等有监听者
   取走 `done` 才完成，无人监听时永久挂起（§13.11）。如果签名是 `Future<void>`，将来
   有人"顺手"把它改成 `await _stream.close()` 就会让 `dispose()` 永不返回；`void`
   让那个 await 根本写不出来。**不要把签名改成 `Future<void>`**，除非同时想清楚
   §13.11 那条挂起路径怎么防。

3. **给计划 3（跳板机）的两条前置条件。**

   - `SSHSocket.destroy()` 在本适配器里退化成 `_conn.close()`（`Connection` 没有
     destroy 的等价物），而 `SSHTransport.close()` 是 `await socket.close()` →
     `await _conn.close()`。**于是任何 `close()` 可能挂起的 `Connection` 都会把拆除
     流程挂住，`destroy()` 这条"立刻走开"的路径也一并继承。** §13.14-7 已记录
     `SSHForwardChannel.close()` 会挂起 —— 所以计划 3 里隧道化的那个 `Connection`
     必须让它的 `close()` 具备 `destroy()` 语义（走 `SSHForwardChannel.destroy()`），
     否则 FR-C-12「退出时关闭所有会话」会卡死。
   - `done` 的完成**依赖对端真的结束 `Connection.input`**。这一点对
     `_SocketConnection` 实测成立（`close()` 与 `destroy()` 之后 `done` 都会完成），
     但它是 `Connection` 实现方的**隐含前提**：计划 3 的隧道 Connection 关掉内层
     channel 时必须让 `input` 结束，否则 `SshSession` 的 `done` 永远不会完成。
